# cliffvm: the field VM as a standalone app

`cliffvm` is the cliffhanger field VM as a process of its own: no Python, no pyo3. The command name is working and
PINNED/undecided; it lives in ONE place, the `[[bin]] name` in `native/Cargo.toml` (the tests read
`CARGO_BIN_EXE_cliffvm`: one more line in `native/tests/cliffvm_process.rs`, and a literal in `cli.rs`'s `build_id` fact).

**The barest seat has no security, by operator decision (2026-11-12).** No JWT, no shared secret, no login, no persons, no
Host/Origin check. The door answers every request: in this mode every request is `authed` with the subject `owner`. The door
opens on 127.0.0.1 unless `--bind` says another address (`--bind 0.0.0.0` opens it to the network: configuration only). The old
JWT code is still in the tree (a later cleanup removes it); the binary neither requires nor uses it.

**The app is a folder of packs (or a pack file).** `main()` parses arguments into Boot facts and runs the apps given; every route, tool,
turn and view is a `.c1f` pack in one (the shipped `membrane/packs/*.c1f` are the app). Several apps are LAYERS and the FIRST is the
root of trust (docs/c1f-layers.md). The Rust side is only the host: the loop, the
drivers, the store, the socket. A decision a pack could make is not made in Rust: if it shows up, it is listed below.

## Build and run

```
cd native
cargo build --release --no-default-features --features bin     # target/release/cliffvm
cliffvm --version
cliffvm run <app> [<app>...] [--store <sqlite>] [--port <n>] [--bind <addr>] [--ui-dir <dir>]
```

- Features (`native/Cargo.toml`): `store` = rusqlite + tls (the native store, the drivers, the door); `python = [pyo3, store]` (the
  seat's `membrane_vm.so`, unchanged: `sh native/build.sh`); `bin = [store]` (the app). A Python extension is not a program, so the
  app is built with `--no-default-features --features bin`. Tests of the app: the same flags.
- `run <app>...`: an APP is a folder `<name>.c1f/` or one pack file (the loader tells them apart). The `.c1f` files of a folder (its
  whole tree) are packs, loaded in dependency order (a pack after the packs of that app it imports; of those ready, the alphabetically
  first path next); every other file is DATA at its path (the door serves an app's `ui/` files). Several apps load in the order given and
  each is a layer above the one before it: a pack whose name is already loaded is skipped (the lower layer's stays).
  **Trust is by position, never by name**: the packs of the FIRST argument are the root of trust (privileged: docs/c1f-layers.md,
  "Privilege"); a later app has no privilege until a privileged pack grants it (`Pack:<name>.privileged = true`; boot.c1f grants
  `door_tools`). A pack named `boot` in a later app is not trusted. The shipped packs are a flat folder, so the shipped line is
  `cliffvm run membrane/packs/boot.c1f membrane/packs`: the single file is the first app (the root of trust), the folder a layer above it
  that skips `boot` (already loaded). The boot plan (`boot.json`, `boot.c1f`) is looked for beside the first app (in its folder, or
  the folder a pack file is in). After the packs: computes the getters once (a rebuild
  runs no setter), runs the boot plan, tells the facts, then `Boot.started`, then loops
  until SIGTERM/SIGINT. `--port` becomes the fact `door_port` (0 = any free port); the pack `door.c1f` answers with
  `Http:door.listen`; once it is up the binary prints `cliffvm: door listening on <host>:<port>`.
- Facts the arguments tell (names as `membrane/packs/facts.json`): `door_port`, `ui_dir`, `app_dirs` (the folders of the apps given, the upper
  layer first; the door serves each one's `ui/` files, an upper layer's file shadowing the lower's; `--ui-dir` stays as the LOWEST layer), `seat_version`, `build_id`, `seat_cwd`,
  `seat_home`, `seat_name` (Bob), `seat_named`, `seat_aliases`, `seat_voice_out`, `seat_language`, `seat_blurp`, and the whole set
  as the dict `facts` (as `boot_started` writes it). There is no `door_secret_file`.
- `--store`: one SQLite file (default `./cliffvm.sqlite3`), WAL: the entity rows (`c_field`: eid -> {cls, props, writers}), the
  journal (`c_journal`), and what `sql(...)` in packs reads (read-only connections of the same process).
  The WAL is folded back and truncated by the clock tick once it is over `WAL_LIMIT_BYTES` (8 MB, `host.rs` `trim_wal`; a reader holding a snapshot stops SQLite's own reset, and SQLite never shrinks the log file by itself; the wait for readers is 50 ms, then the next tick tries again). The main file does not shrink after rows are retired (freed pages are reused, `auto_vacuum` is off); test `native/tests/wal_1143.rs`.
  DURABILITY: the store is WAL with `PRAGMA synchronous = NORMAL` (`Host::open`; the operator approved it, the Python store does the same): a commit is not fsynced one by one, so a power loss (not a process crash) may lose the last commits, never corrupts the file; a clean restart keeps everything (test `finished_guard_1143.rs`).
- The boot plan: this host runs none of the plan's steps (they are the Python seat's), so each is `skipped` and the plan only says
  when the boot is over. Then `started`.

## Run a seat

The barest usable agent seat: one command starts `cliffvm` on the shipped packs and the barest app, and the page is a graph viewer plus the one chat.

```
(cd native && cargo build --release --no-default-features --features bin)      # once; the launcher builds nothing
scripts/seat [--store ./.cliffvm/seat.sqlite] [--port 4096] [--open] [--fact name=value ...]
```

It runs `cliffvm run <the packs of membrane/apps/barest.packs, one file each> membrane/apps/barest.c1f --store <sqlite> --port <n> [--fact name=value ...] --fact chat_claude_bin=<claude>`
from the repo root and prints the URL. `CLIFFVM` names the binary (else `native/target/release/cliffvm`, else PATH); `CLAUDE_BIN` names the claude CLI
(else the one on PATH; with none, the seat starts and the chat answers with how to name it). The chat needs `ANTHROPIC_API_KEY` in the environment, or `CLAUDE_AUTH=login` to use the claude CLI's own login (docs/cliffvm.md, "The claude turn's auth"). `--fact name=value` (repeatable) is passed on as a Boot fact (`--fact warm_rows=0`). `--open` opens the page on macOS. The launcher starts nothing else
(no Ollama, nothing under `~/.membrane`) and uses no port but `--port`.

**What you see** (`membrane/apps/barest.c1f/ui/`: `index.html`, `app.css`, `app.js`, `mcp.js`, `graph.js`, `chat.js`, `chatmount.js` (the legacy chat is the default; the view pack `chat_view.c1f` only for the fact `ui_views` or `?ui=pack`, docs/ui-rebuild-plan.md); plain static JavaScript served by the door
from the app folder, no build step, no dependencies; a later piece ports it to c1f view packs in the browser VM):
- Left, the GRAPH VIEWER: every entity as a node (a canvas force layout written for this page: repulsion, springs, centring, pan, zoom, node drag), coloured by class.
  Edges are ownership (`A:b:c` hangs under `A:b`, or under its nearest listed ancestor) and references (a `{"$ref": eid}` value or a string that is another listed eid, dashed).
  It polls every 3 s keeping positions, has a substring filter, a `requests` switch (the door's own Request entities are hidden by default), a list view, and a side panel with the
  selected entity's properties (a reference is a link). Keys on the canvas: arrows pan, `+`/`-` zoom, `0` fits.
- Right, the CHAT: the history is the chat's entities, so a reload brings it back; Enter sends, Shift+Enter adds a line; a running message is read from its event stream (see "The event stream": the answer appears as it is written; the page falls back to polling it every 700 ms only when the stream cannot be had) and
  shows the tools Claude ran with a short input. An answer that asks for something (no CLI named) is shown as a note.
- The graph reads through `POST /mcp` (`entity_query`, `entity_read`); the chat reads `/membrane/chat/messages` (history) and `/membrane/chat/message/<id>/events`.

**`entity_query` additions for the viewer**: `offset` (paging), `kind!:<Class>` (all but a class) and `full` (rows carry the stored properties).
**Data** is the `--store` file (default `./.cliffvm/seat.sqlite`).

**The barest packs** (`membrane/apps/barest.packs`, one shipped pack name per line in load order; `scripts/seat` and `seat_process.rs` read it): `boot door fs proc fetch store door_tools chat chat_turn`,

`router`, `decisions`, `dev`, ...) stay in `membrane/packs/` for the Python seat and are NOT loaded here: a request carries none of their getters, and the seat seeds no

**Door requests are garbage collected** (`Request` is VIRTUAL; "Garbage collection of virtual entities" below). Read the live ones with `run_cliff` and `instances('Request')`.

predecessors' whole state and the sizes doubled per request (a 100-row query reached megabytes and the engine stopped answering).

The model reads them with `entity_read` and lists them with `entity_query` `kind:Help`; the doctrine in `chat_turn.c1f` says "Use Help entities for help" and `Help:c1f` tells where the topics are and how to list them. `help/banner.md` (`Help:banner`) teaches the banner.

The value kind `Error` (a failure, distinct from null) and the `is` operator are built (#1143): `docs/c1f-error.md`, `Help:c1f`.
(ownership, rule B, layers), `upgrade` is what changed since 0.7.53 plus a SQL / Vue / JavaScript lookup table. **Every code block is a test**: `native/tests/help_1143.rs` loads each ```c1f block through the

**The return entity** (#1143, operator-approved 2026-11-13; `door_tools.c1f` `mc_w_*`, `host.rs` `reactions_of`): `entity_write` answers in ONE call with
what the write caused. The reply is `wrote <id>.<prop>`, then (a) for a write that starts an effect (`File.write/move/delete`, `Command.run/stop`, `Store.run`, `Fetch.request`, `SqlQuery.run`: an explicit list in the pack) the RECEIPT, the
`<prop>_result` of the entity: the line `receipt: {id, status, rc, ok, started, finished, ms, stdout_bytes, stderr_bytes}` (`started` and `finished` are epoch seconds taken by the Command driver around the run, `ms` its duration: a rerun with the same id and the same output is a NEW receipt because the timestamps differ, and parallel runs can be checked for overlap; the driver keeps no receipt counter), then `stdout: {...}` and `stderr: {...}` (a run the driver refused, with no output, adds `error: <reason>`; a stream of at most 16 KB comes whole as `stdout`; a longer one as `stdout_head` and `stdout_tail`, the first and last 8192 characters, `mc_w_cap` in `door_tools.c1f`; the reply no longer repeats the output as `head`). The FULL text stays on the Command (`Command:x.output`, `Command:x.errors`) and the reply says `full output: read Command:x.output`: the Claude CLI refuses a tool result over its MCP limit (default 25000 tokens, raised by the env var `MAX_MCP_OUTPUT_TOKENS`; this seat does not set it) and the model then gets nothing (a 50 KB output made a 54 KB reply). Or `pending: id: <run id>, status: running, started: <clock>; read <id>.<prop>_result later` when it is not there (a Command in flight also reads `status: running` and `running: {id, started}` on the entity: the engine notes `running` when it takes the `run`, `proc.c1f` `Command.status` reads running until a receipt that finished after it lands; none before any run) (a receipt equal to the one there before the write is not this write's);
(b) the REACTIONS (REAL changes only: the consumed verb slot, `run -> ""` by `direct:consumed`, and a birth's none-to-none `rebuild` of a getter are dropped, a none that carries a `why` stays): the host (`Host::reactions_of`, `drain_apply`) takes the batch the engine wrote in the round of the door's `mcp-write` setter and tells it back on that Request as `reactions` (a derived write, never journalled, a replay drains the same
way): every derived write of the batch except the door's own bookkeeping (Request, Return, Pack), the last value per property, each `{eid, prop, new, by, why, cls}` (`by` = the setter or getter that wrote it, `why` = the reason of a null, `cls` = the entity's class as `this.cls` reads it, a host field: the first non-Error class of its `parents`, not the eid prefix). The MODEL-FACING reply does not print them all (design B2 of `docs/reply-size.md`, operator 2026-11-14; `door_tools.c1f` `rx_*`): the line `reactions: [...]` lists IN FULL the reactions on the WRITTEN entity (the target) and its direct children (`<eid>:...`; for `run_cliff` those set by the block's own setter `run`) plus EVERY reaction that carries a reason (a null with `why`, an Error's `failed`), on any entity; the line `other changes: Banner.text x1, Chat.argv x10` counts the rest as `<Class>.<prop> xN` (no values, no example eid, no `by`; read an entity to see its value). The field `reactions` on the Request and the JSON routes are unchanged. Measured on the 8 writes of the doc (`chat_process.rs` `a_keep_write_with_running_turns...`, `a_mention_write_answers_small...`): Keep with 10 running turns 134 KB -> 0.5 KB (the 264 KB of the doc had more text per message), a `mention` 60 KB -> 2.4 KB. The round is the batch of
that write; what a setter's effect does later arrives as a receipt, not as a reaction. A parallel call's batch may carry the other call's reactions: the engine is one thread and a batch is a batch; (c) the RETURN ENTITY `Return:call:<request number>` (class `Return`, declared by `door_tools.c1f`: `tool`, `target`, `written`, `result_prop`, `reactions`, getters `receipt`, `state`) is a TRANSIENT CARRIER of the reply (operator, 2026-11-13): the reply is held until it exists
(`mc_w_returned`) and it is collected as soon as the reply is delivered (the Request holds it by a reference, `mc_w_returned`, and is itself held by its connection until the `respond` receipt is taken: "Garbage collection of virtual entities"); it is not stored memory, the reply does not name it, and no boot fact keeps it. The receipt stays where it
always lived: `<prop>_result` on the target entity. The optional `wait` (seconds) holds the reply until the receipt or that many seconds
(a `clock` getter, one tick of resolution) and then answers `pending`; with no `wait` the reply is made at once. The reply is held by the existing pattern (`mc_w_text` stays null until `mc_w_returned`). **One write starts a command**: `Command:x.run = {id, cmd: [argv]}` (or a string for `sh -c`) runs the value's `cmd` and the engine keeps it on the entity (`fields.rs` `driver_effect`, writer `driver:cmd`), so later runs may leave it out; the two-write form (`cmd`, then `run`) works as before. Tests: `chat_process.rs`
(`a_write_that_starts_an_effect...`, `a_write_returns_the_reactions...`, `the_return_entity_is_retired...`, `two_slow_commands...`, `the_effect_workers_fact...`).
**Parallel effects and `effect_workers`**: an effect runs on its own driver thread and a held request blocks nothing (the door's threads and the engine go on), so two slow commands started by two parallel tool calls finish in about the time of one. The slow drivers
(`Command.run`, `File.*`, `Fetch.request`, `SqlQuery.run`; `Store::effect_limited`) take a WORKER SLOT: at most `effect_workers` (Boot fact, `--fact effect_workers=<n>`, default 4, operator-approved) run at once, the rest wait for a slot. The chat's turn is a `Command.run`, so it holds one slot while the model runs;
the door's listener, a held request, an open event stream and `Command.stop` take none.

**A command's time limit** (`drivers.rs`, `proc.c1f`; operator request 2026-11-13, after a model-run `grep -r` over the whole projects tree ran 71 minutes and held a worker slot): `timeout_s` is the model's own estimate of the longest a command may run, in the run value
(`Command:x.run = {id, cmd, timeout_s: 600}`) or set on the entity before the run. Without it the Boot fact `command_timeout_s` applies (default 120 s, the operator-delegated sensible default; the Python-era Mirror limited commands to 60 s).
There is no upper bound and no unbounded command: 0 or less (or a non-number) is refused with a reasoned receipt, a long job states a big number. The child leads its own process group; at the deadline the group gets SIGTERM, after `KILL_GRACE_MS` (2 s) SIGKILL;
the worker slot is freed when the run ends. The receipt: `status: "timeout"`, `rc: 124` (the convention of GNU `timeout`), `killed: true`, `timeout_s`, `ms`, the partial stdout/stderr (the reply's 8 KB head/tail rules apply); a run in time carries `timeout_s` too
and no `killed`. The receipt is the journalled outside write like any driver receipt: a replay runs nothing, so there is no clock in it. `Command.stop` kills the same group at once. A timed-out run's `output`, `errors`, `ok` and `rc` are REASONED NULLS
(`why(Command:x.output)` = `Command:x timed out after N s (killed); start it again with a bigger timeout_s, e.g. run = {id, cmd, timeout_s: 600}`; getters built on them pass the null and the reason on); `partial_output` / `partial_errors` hold what was read, `run_rc` stays the raw 124.
The write reply says the same in a `timeout:` line; the pending reply shows `timeout_s` and the seconds `left`; `running` = {id, started, timeout_s}. The chat turn's own `claude` run states `timeout_s` = `chat_turn_timeout_s` (default 21600 = 6 h, a threshold flagged for the operator), so the default never kills a turn.
Tests: `chat_process.rs` (`a_command_past_its_timeout_s...`, `a_timed_out_commands_result_props...`, `a_command_that_finishes_in_time...`, `a_timeout_s_of_zero_or_less...`, `without_a_timeout_s...`, `a_timed_out_command_frees...`, `the_chat_turn_is_not_killed...`).

| Boot fact | default | meaning |
|---|---|---|
| `command_timeout_s` | 120 | limit of a Command run without `timeout_s` |
| `chat_turn_timeout_s` | 21600 | limit of one chat turn's `claude` run |

**The turn's numbers** (`chat_turn.c1f`): the result line of the CLI's stream carries `usage` {input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens}, `total_cost_usd`, `num_turns` and `duration_ms`; the finish writes them on the turn
entity (`...:turn`) as `usage`, `cost`, `calls` and `duration`, and the message view's `turn` (and so the event stream's events) carries them. A run that ended with no result line has none. Test: `chat_process.rs` `the_turn_carries_usage...`.
**Finished messages stop reading the banner** (`chat_turn.c1f`): the per-message prompt getters (`bin`, `max_turns`, `port`, `mcp_json`, `banner_text`, `banner_slot`, `sys`, `argv`, `note`) are `WHEN this.over: None`, so once the turn is done/error they hold none (derived, cleared in the store) and no longer depend on the banner: a banner change recomputes only unfinished messages. Measured on the fake seat: the reply of an `entity_write` that changes the banner was 61871 bytes with 50 finished messages (121 without), and is 121 bytes with 50 now (tests `finished_guard_1143.rs`, `chat_process.rs` `a_banner_change_returns_reactions...`).

**Resource hygiene** (`chat_turn.c1f` `spent`, `slim-run`): once a turn is over (done/error) the Command's receipt `run_result` is replaced by `{id, status, rc, stderr}` (the raw stdout and its twin `head` were each stored again with the getters' cached parses, hundreds of KB a turn);
the answer, the tools and the numbers are entities. The finish (`turn-finish`) runs only while the turn is not over, so the slimming's recompute leaves the response alone. The raw lines are no longer in the JOURNAL either: a `Chunk` is VIRTUAL (never stored, never journalled; it was about 1.6 times the
raw output, 324 KB for a 200 KB turn, when it was journalled). Test: `chat_process.rs` `a_finished_turn_keeps_its_answer...` (rows under a 16 KB bound).

**Memory of the seat** (w28, #1143): a synthetic burst (two parallel messages of 1500 stream chunks each, a 1 MB command output, a polling page and two event streams) took the seat from 122 MB to about 2 GB. The counting allocator showed it was LIVE data, not allocator retention: the core's trigger queue (`Core::q`, `vm.rs`), a ring of the last 4096 writes with their whole `old` and `new` values, is read only by the Python-era trigger engine; a field host never reads it, so it held every big getter value (the message's chunk list, the joined partial text) for nothing. `Core::queue_writes` is false in a field host (`host.rs`, the Python `Fields`, the wasm `Field`) and `hear` keeps nothing then (test `queue_1143.rs`). The same burst: peak RSS about 2.0 GB to about 0.2 GB, live bytes peak 1.65 GB to 0.11 GB, burst CPU 52 s to 12 s (with the chunk fix above). `malloc_zone_pressure_relief` after the turn was measured and gives about 20 MB, so it is not called.
The diagnostic: `cargo build --release --no-default-features --features bin,alloc-stats` (OFF by default; the module is not compiled without it) installs a counting global allocator in `cliffvm` (`alloc_stats.rs`) and prints to stderr one line a second, `alloc-stats t= live= peak= total= allocs=`, and every 2 s a `mem-breakdown name=entries/KB ...` line (entities by class, `why`/`locals`, the reverse-reference indexes, the field's `out`/`deps`/`reads`, the store's receipts / inbound / queued stream frames, the in-memory journal, the open transaction's rows). Live bytes against RSS tells retained data from freed pages the allocator keeps. On macOS `MallocStackLogging=lite` plus `malloc_history <pid> -callTree` names the allocating call path of what is live (that is how the queue was found).

**`run_cliff`** (#1143; `door_tools.c1f` `cl_*`, `help/cliff.md`): the fourth MCP tool, next to entity_query / entity_read / entity_write (none removed). A CLIFFLET is a small block of the getter-body syntax (locals, the last line is the value) run in one call. Built from existing parts:
the door writes TWO scratch Pack entities at once, `cliffg<n>` (the block as the body of a getter `val`, plus `shown` = `{v: val, why: why(val)}`) and `cliffs<n>` (the block as an on-setter body `go`; privileged, so a block may write any class like `entity_write`,
imports door/fs/proc/fetch/store), each with a class of its own (`Cliffg<n>`, `Cliffs<n>`). Both packs carry `scratch = true`: `instances(<Class>)` does not list an entity with `scratch = true`, so a block listing `instances('Pack')` sees the field's packs, the same set as `entity_query kind:Pack`, not its own scaffolding (an explicit property, not a name rule; test `a_clifflet_reads_eid_cls_and_parents_and_lists_the_same_packs_as_entity_query`). `eid`, `cls` and `parents` are what an entity reads next to its properties (Help:cliff says so). Whichever loads decides the mode: a block that loads as a getter is a VALUE (the scratch entity `Cliffg<n>:x` is born by a write and `shown` is read); one that loads only as a setter body is WRITES
(`Cliffs<n>:x.go = True`, with `mc_done` so the host tells back the reactions of the round exactly like `entity_write`, `reactions_of` accepts the setter `cliff-run`); one that loads as neither answers `the block did not load.` with both loader messages. The value comes back as text (`str`: JSON for a list or dict, a plain
null is `null`), a null with a reason as `null: <reason>` (`isError` false: nothing failed) and a failure (an Error) as `Error: <reason>` (`isError`), so a runaway block answers `Error: budget exceeded (N steps)` under the engine's step budget (time limits nothing, so a slow block still answers its value) and the seat goes on. The size of the answer is not capped. A write that starts an effect has its receipt in a later round (`<verb>_result`). After the answer the setter
`cliff-finish` stores it (`cl_final`) and retires the scratch entity and both packs (the pack text is emptied, then retired). Tests: `chat_process.rs` (`a_clifflet_reads_and_joins...`, `a_clifflet_that_writes...`, `a_runaway_clifflet...`: 20 calls of four shapes leave the entity count and the pack count as they were); `help_1143.rs` runs every ```cliff / ```cliff-write block of `Help:cliff`.
Costs: loading a pack (a cliff call loads and removes one) recomputes only the getters the load changed or added; a getter the new set carries unchanged keeps its value and its inputs, and the getters of one property name count as changed together (they stack their arms; `Fields::set_getters`, test `idle_getters_1143.rs`; before, every getter of every entity was evaluated again, `Command.timeout_default` about 90 times a second on a seat with ~200 commands and a model calling `run_cliff`). A call is as slow as the seat is full (a seat that kept its answered requests took seconds per call in a debug build; the engine collects them now).

**The banner** (`membrane/apps/barest.c1f/default_banner.c1f`; the Python-era `banner.c1f` is not loaded here): `Banner:owner:main` (spelled `membrane::Banner:owner:main`, the chat's namespace) is the entity `chat_turn.c1f` reads into every turn, and it is
FULLY the model's: the seat never segments, orders or joins what the model puts there, and its `text` is a getter (cached, recomputed when what it reads changes), so the banner is live by nature. The static instructions (what the banner is for,

**Storage modes** (#1143, operator 2026-11-13; `native/tests/storage_1143.rs`, `lazy_boot_1143.rs`): a class has one of three modes, declared by the pack that OWNS the class in its header, one class per line, like `IMPORT`
(`docs/c1f-layers.md`, "Header lines"). The mode is by the entity's own class (its eid's; `membrane::Chat:message:1` is `Chat`):

| mode | header line | stored | loaded | journalled | `entity_query` |
|---|---|---|---|---|---|
| virtual | `VIRTUAL <Class>` | no row | RAM only, never restored | no | no (it is not a row) |
| resident | `RESIDENT <Class>` | yes | ALWAYS: at start, and the moment a pack declares it | yes (outside writes) | yes |
| (default) lazy | none | yes | ON DEMAND, see below | yes | yes |

- **Shipped declarations.** VIRTUAL: `Request`, `Return`, `Chunk`, `Step`, and `Boot` and `Http` (see "What `PER_RUN_CLASSES` did"). RESIDENT: `Pack`, `Banner`, `Help`, `Command`, `File`, `Dir`, `Fetch`, `Store`, and every class a pack lists
  whole with `instances(...)` (`Attention`, `Model`, `Minds`, `Intent`, `Goal`, `Task`, `Wait`, `Decision`, `Seat`, `Ctx`, `Tool`, `Message`, ...) or whose driver is a sensor (`Peer`, `McpServer`, `Memory`). Everything else is lazy (`Chat` and its messages, turns, responses
  and tools). A test lists every `instances('X')` in the shipped packs and refuses one whose class is not declared (`a_class_a_pack_lists_with_instances_is_loaded_whole_or_is_virtual`). Only the owner declares a mode (a storage line claims a
  class no pack owns yet); a class cannot be both; a refusal names the pack that owns the class and what it declares.
- **VIRTUAL semantics.** Never stored (`store_born`/`store_prop` skip it), never restored, never journalled (`journal_push` skips a line about it). The engine keeps it, so a getter, a setter, `instances`, `prop(<id>, ...)` and a block run by `run_cliff` read the LIVE ones;
  `entity_query` and `entity_read` without a `prop` read the store and do not see them. What a setter writes to a stored entity while a virtual one triggers it (a chat message born by a setter on a `Request`) could not be derived again by a replay (its trigger is not in the journal),
  so the host stamps it `host:virtual:<setter>`, an OUTSIDE write: journalled with its time, and a replay of the journal ends in the same state. Only the first hop is stamped: what that write's own setters and getters make is derived again by the replay.
- **LAZY LOAD** (`Core::unloaded`: eid -> class, noted at start from a covering index on `(cls, k)`: no body is read). A stored entity loads on its first REFERENCE: a read by id or entity literal from a getter, a setter, a block or the door tools (the evaluation finds nothing, the engine loads the row at once and evaluates again,
  `Core::fault_now`); a write (an outside one, or a setter's: `Fields::ensure` before the target is looked for, so a setter never makes an entity that is stored); `Host::get`. A loaded row brings its stored properties (a getter's stored value too: the read is right away), its getters recompute (the stored value stands until they do) and what read its fields or listed its class recalculates.
  **`instances('<Class>')` lists the entities whose eid class is `<Class>` AND those that carry it as a kind in their `parents` list (`instances('ChatMessage')` lists the messages, whose eid class is `Chat`); for a LAZY class only the entities that are LOADED** (a class that was never referenced since the start may list none); a RESIDENT class lists all of them, a VIRTUAL one all the live ones. `referencing(x, 'prop')` likewise sees only loaded referrers. A getter that must see every
  stored entity of a class declares the class RESIDENT, or asks the store (`sql(...)`: the barest `Boot.interrupted` finds the turns a run left `running` that way; a `sql` getter's answer is cached, so it is a start-up read). Door tools `entity_query` and `entity_read` (no `prop`) read the store: complete, whatever is loaded.
  `instances` walks the loaded entities once per class: the sorted answer is kept per class (lower-cased) until an entity THAT CAN BE IN IT arrives, leaves, changes its class or writes `parents` / `scratch` (`Core::inst_touch`; a `Request` being born no longer drops `instances('Boot')`; walks are counted, `Host::inst_scans`), and the class test reads the `parents` entries without building a list (`Ent::in_classes`). Before, every call walked 30,000-60,000 loaded entities building a list of Strings each (3-5 ms a call, eight calls a request: a request for one row cost 80 ms with a big session loaded, 29 ms now; `native/tests/instances_cost_1143.rs`, which counts walks).
  A retired entity takes its stored, unloaded children (`A:1:x` under `A:1`) with it. A runtime pack that declares a class RESIDENT loads its stored rows at once. An entity can also leave the engine again: "Eager unload" below.
- **WARM BOOT.** At start the host loads the packs, then the RESIDENT rows (restore rules as before: a getter's stored value is not read back, the rebuild computes it again), notes the rest, and the loop serves: the door answers at once. In the BACKGROUND, between turns of the loop, the newest-`updated`
  unloaded rows load, `WARM_SLICE_ROWS` (64) or `WARM_SLICE_MS` (20 ms) at a time, up to the boot fact `warm_rows` (`--fact warm_rows=<n>`; default `DEFAULT_WARM_ROWS` = 1000; 0 = none). The three numbers are thresholds, flagged for the operator.
  Numbers (release build, synthetic Note rows of ~250 bytes, one machine): 5,000 rows: door up in 0.67 s / 56 MB before, 0.12 s / 15 MB after; 50,000 rows: 6.8 s / 388 MB before, 0.33 s / 26 MB after; a copy of the real repro store (470 rows, 18 MB): 4.5 s / 184 MB before, 0.37 s / 40 MB at the door (72 MB after the warm boot).
- **`updated`** (a VM-provided, READ-ONLY property of every entity): the epoch time of the entity's last write. The host stamps it with the write, in the same row and transaction (`c_field.updated`, indexed; next to it `cls`, indexed: the restore loads the resident classes by it). No extra write, no reaction (a setter on `updated` never fires), no getter recompute (a getter that read
  it keeps what it read until something else it reads changes); a setter that writes it is refused (a receipt), an outside write of it is dropped (not journalled). Derived writes take the time of the outside write that started their round, so a replay (which applies the journal's recorded times) ends with the same `updated`. A virtual entity has it too (RAM).
  Read it as `<entity>.updated` from a block or a getter, or `entity_read {spec, prop: 'updated'}`. A store of an older shape is migrated at open: the columns are added, `cls` is filled from the body, `updated` from the journal's last line about each entity (0 when the journal never names it: only outside writes are journalled); once, never over a later stamp.
- **EAGER UNLOAD** (#1143, operator 2026-11-13; `native/tests/unload_1143.rs`, `unload_process_1143.rs`): the opposite of lazy load. An entity not touched for a while leaves the engine, its row kept, and the next reference loads it again (the lazy path above). It is driven by memory pressure, in four pieces:
  - **The sensor** (`Host::sense_memory`, `host.rs`): at every host tick (1 s) it writes `Mem:host` (an outside write like the clock's tick, stamped `host:sensor:mem` and NOT journalled: a reading of this process is not history, so a replay never sees it and never repeats an unload it caused). `rss` is the resident size in bytes (written again only when it moved by 1 MiB, `MEM_STEP_BYTES`: an idle seat is not rewriting a row every second), `budget` is `memory_budget_mb` in bytes (only when the fact is set), `level` is `ok`, `soft` or `hard`:
    no budget = always `ok`; else `hard` from `unload_hard` x budget (the budget itself when unset), `soft` from `unload_soft` x budget (no soft level when unset), else `ok`. `level` is written on a change AND at every tick while it is not `ok`: that is one policy pass per tick for as long as the pressure lasts.
    It runs only when a pack declares the class `Mem` (the barest app's `unload.c1f`, which declares it RESIDENT): a host without that pack writes nothing. The resident size is `process_rss()`: `task_info(MACH_TASK_BASIC_INFO)` on macOS, `/proc/self/statm` on Linux (the `libc` crate, already a dependency; nothing on other targets: the sensor then does not run). TEST ONLY: `MEMBRANE_TEST_RSS=<path of a file holding the size in bytes>` replaces the reading (`cli.rs`; read at every tick; an unreadable file falls back to the real one), or `Host::set_rss_reading` in-process.
  - **The facts** (the operator's numbers; NONE has a default, and none is chosen here): `memory_budget_mb` (unset: the level is always ok and nothing unloads), `unload_soft`, `unload_hard` (fractions of the budget), `unload_batch` (how many entities a pass asks for; unset: no unloading). The soft and hard levels both run the pass: `unload_soft` unset means there is no soft level, so nothing unloads below the hard line.
  - **The policy** (`membrane/apps/barest.c1f/unload.c1f`, c1f): `Mem.level on-setter unload-coldest` picks the `unload_batch` entities with the smallest `.touched` among the loaded ones that `.pinned` lets go (`instances('Entity')` lists every loaded entity) and writes `unload = True` on each. The pack is privileged (it writes any class): `boot.c1f` grants it with `door_tools`. It stops by itself: the pass runs only while the level is not ok, and a pass over entities that are all pinned unloads nothing.
  - **The primitive** is ONE write, `<entity>.unload = true`, like `retire`: any writer (a setter, the model's `entity_write`; an outside one is journalled like any outside write, and a replay unloads again, which changes no value). `unload` is a request, never a property: it is not stored, the row and its `updated` stay as they were. The entity leaves the engine (`Core::unload`, `Fields::unload`: its properties, its place in the load order, the engine's memory of its last evaluations, its own getters' read lists) and is noted in `Core::unloaded`; nothing is written back (the store is written through at the end of every round, so the row already is the entity). Only STORED entities of a LAZY class go. **PINNED**, refused with a receipt `unload_result` = `{status: refused, reason}` on the entity (the slot is consumed, so a later `unload = true` fires again): the class is virtual (no row to come back from) or resident (packs, drivers, `Mem`, everything a pack lists whole), a running effect (`running` set), or a live VIRTUAL entity holds it by a `$ref` value (a request still being answered holds what it points at). The VM property `<entity>.pinned` is `False` or that reason as text (core-side reasons; the `$ref` pin is the host's), so the policy filters on it.
    **What depends on an unloaded entity** (the simple SAFE rule): nothing is marked dirty and nothing recomputes. A getter that read it keeps its cached value (an unload changes no value); when that getter next recomputes and reads the entity, the read loads it again (`Core::fault_now`), and an arrival makes the readers of its fields recompute as any load does. A write to it loads it first (`Fields::ensure`). So a dependency never sees a hole, and an entity that is read all the time is hot, hence never among the coldest. A cached `instances('<lazy class>')` keeps naming an unloaded entity until it recomputes; `instances` and `referencing` list only what is loaded (documented above).
  - **The touch clock** (`.touched`, `Ent::touched`, `Core::clock`): a counter in the core bumps at every read of a stored property (an evaluation's attribute read), every write that reaches the entity and its load; the entity keeps the counter's value. RAM only, never stored, never journalled. `.touched` is read-only and VM-provided like `.updated`; reading `.touched`, `.updated`, `.eid`, `.cls` or `.pinned` touches nothing (the policy's own scan must not heat what it reads). The entity's reads by the door's store-reading tools (`entity_query`, `entity_read` without a `prop`) do not touch it: they do not read the engine. **Exception**: an entity that STORES a property named `touched` (the Python-era `Turn.touched`, `turn.c1f`) reads its own: the clock does not shadow a stored value, and a setter that writes `touched` writes that property. The cost: a counter increment and two `Cell` stores per read, 0.56 ns measured (release build, `unload_1143.rs` `the_cost_of_the_touch_clock_per_read`, run by hand with `--ignored`), against about 255 ns for a whole evaluation of `this.n`.
  - Complexity: a pass is O(loaded entities) for the c1f sort, once per tick while the level is not ok; an unload is O(its own getters and dependency edges), and the batch's pin check builds the set of `$ref` targets of the live virtual entities once per drain. The load order keeps a hole per removed entity and closes them when they outnumber the live ones (amortised O(1)), so load/unload cycles do not grow it.
  - **Flagged thresholds**: the sensor period (the host tick, 1 s), `MEM_STEP_BYTES` (1 MiB), the hard line = the budget when `unload_hard` is unset. The levels' behaviour (soft and hard run the same pass) is a choice the operator may change.
  - Tests: `unload_1143.rs` (touch clock, primitive, equal reload, reload on write and on a getter dependency, `instances` after unloading, pinned refusals, `$ref` pin, the pressure loop with an injected resident size, no budget / no batch / no soft, restart, replay), `unload_process_1143.rs` (the binary with `MEMBRANE_TEST_RSS`).

- **GARBAGE COLLECTION OF VIRTUAL ENTITIES** (#1143, operator 2026-11-13; `native/tests/gc_1143.rs`, `chat_process.rs` `a_request_is_collected_right_after_its_reply_...`): a virtual entity (`Request`, `Return`, `Chunk`, `Step`, `Boot`, `Http`) is collected at the END OF THE ROUND in which nothing holds it any more. No pack retires it (`Host::drain_apply` runs the collector last, `Core::gc_dead`; removing the dead is a round of its own, as a retire is, and drains again). Only VIRTUAL classes: a stored entity keeps its explicit `retire` and the unload above.
  **Holders.** (1) OWNERSHIP: a colon-path child lives while its parent ENTITY lives (`Request:7:body` with `Request:7`; the parent of `a:b:c` is `a:b`, and it must be an entity). (2) A REFERENCE: a live entity has the virtual entity's id as a `{"$ref": "<id>"}` value in a property, at any depth (a list, a dict). That is the form the engine already stores an entity VALUE in (`V::Ent`), so a setter writes `this.keep = Req:made` (or `[Req:made]`), a getter that returns an entity (or a dict or list holding one) holds it, and `x = None` releases. The engine keeps a reverse index of these values per (holder, property), current on every write, load and removal (`Core::ref_in`; the cost per write is one lookup and a walk of the new value). (3) IN-FLIGHT drivers (`Store::holds`, `conn_held`, `Core::in_flight`): an open connection (`Request.conn` still in the store's held connections, or an open event stream: until its `end`), an effect started on the entity whose receipt the engine has not taken yet (a `respond`, a `stream`/`send`/`end`, a `verify`, a `listen`), the listener an `Http` entity opened, and an effect on an entity named inside its id: `Chunk:<command eid>:<n>` is held while the Command has an effect in flight (the chunks of a run). A held `wait` reply holds its Request through its open connection.
  **A plain read holds nothing**: a getter that peeks, an entity literal in an expression, `prop(...)`. What holds is a VALUE that is stored. **Roots**: every non-virtual loaded entity, packs, the drivers' in-flight work, and the host's own: `Boot:seat` (`Host::hold`, called by `boot_started`) and the boot plan's steps (`Core::host_held`). A loop of virtual entities that hold each other and nothing else is unreachable: both are collected (`Core::held` walks the holders of an entity with a visited set; it finds a root or it does not).
  **When, and what it costs.** A candidate is an entity born this round, or one that lost a holder (a reference written away, a holder collected, a holder removed), or one whose effect receipt the engine took this round (and then the live entities that name it as their owner). Only candidates are looked at: no scan of the field per round. A candidate costs the length of the chain of holders it walks (usually 1; a Request is held by its connection at once); an effect's end costs one pass over the LIVE virtual entities (`Core::virt_live`) to find the ones that name it; a dead entity releases what it held and its colon-path children, and the pass goes on until nothing new dies.
  **A read of a collected entity** is a null with the reason `collected: nothing held it` (`V::Nil`, as `why(...)` reads it); the last `COLLECTED_KEPT` (4096, flagged) ids are remembered for that, older ones read as a plain missing entity. Writing to a collected entity is dropped as a write to any missing one. A Request that the client abandoned before the pack answered is held by its connection forever (as it always was); an answered one is gone with its reply.
  **What it replaced** (the barest app's `collector.c1f`, `door_tools.c1f`, `chat_turn.c1f`): `Request.answered`, `Request.expired`, `dropped`, `kept_at`, `keep_s` and the retire writes for Request; the Return's setter-based retire (`mcp-return-retire`, `mc_w_sent`, `mc_w_ret`: the Request now HOLDS its Return by reference, `mc_w_returned` is `Return:call:<n>` as a value, so the Return goes with its Request); the chat turn's `stale_chunks` + `retire-chunks` (the Chunk is held by the Command's in-flight effect; once its receipt is taken nothing holds it). `collector.c1f` keeps ONLY the start-up sweep of the stored Request rows an older run left (they are stored text). The fact `request_keep_s` is still ACCEPTED (`--fact request_keep_s=<n>`; the launch lines that pass it do not break) and does nothing: no pack reads it.
  **An entity that holds a live virtual one cannot be unloaded** (it is pinned, `.pinned` says so): unloading would drop the reference and the virtual entity would be collected under whoever still wants it.

**What `PER_RUN_CLASSES` did.** The old list (`Boot`, `Http`, `Request`, `Step`) kept those classes out of a restart: their rows were stored text and the new run made them again. Its job is `VIRTUAL` now, and those four are declared VIRTUAL (`boot.c1f`, `door.c1f`): the restore skips them as before, and
a row an older run stored stays text (the collector's start-up sweep still retires old `Request` rows). Two things differ for `Boot` and `Http`, which were stored and journalled: they are no longer rows (`entity_query kind:Boot` is empty; `entity_read Boot:seat` with a `prop` still reads the live entity), and the boot facts are not in the journal, so what the
`Boot.started` setters write to stored entities (the Help entities, the banner seed, the grant of the tools pack) is journalled as outside writes (`host:virtual:<setter>`): a replay ends in the same state except the Boot entity and the grant's `granted_by`, which names the host that replayed it.
(RESIDENT could not stand in for them: a restored `Http:door.listen_result` would make the seat announce the previous run's port and the unchanged `listen` write would never start the listener.)

**Restart restores the entities** (`host.rs` `load_stored_entities`, called by `cli.rs` after `load_stored_packs` and before the rebuild): the stored `Pack` rows first, then the RESIDENT classes' rows arrive in the engine with their class and props
(the `parents` stamp is a prop); every other row of a lazy class is only noted and loads on reference or in the warm boot (above). A prop a getter wrote (`trigger:field:getter:*`, `rebuild`) is not read back for a resident row: the rebuild computes it again, so a changed getter shows its new value. A VIRTUAL class's row is skipped. No setter runs on a restore and nothing is rewritten.
A turn that was `running` when the seat stopped (its Command had no receipt) is marked `error` at start, with the response `interrupted: the seat stopped while this turn was running` (`chat_turn.c1f`, `Boot.interrupted`: a `sql` over the store's running turns that started before this run's `Boot.started`; the turns are lazy, so the engine's `instances` cannot be asked).
The banner's previous-turn line reads the chat's `last_turn` (a turn that ends writes its eid there, `chat_turn.c1f` `last-turn`), one reference instead of a list of turns; a chat from before the pointer has none until its next turn ends. A turn left `queued` is not touched. Tests: `seat_process.rs` `a_restart_restores...`, `the_previous_turns_error_is_still_in_the_banner_after_a_restart...`, `chat_process.rs` `a_turn_that_was_running...`, `an_interrupted_turn_is_found_in_the_store...`.

**An entity of several classes: the class list** (#1143): an entity has NO privileged own class. Its classes are ONE ordered list, its `parents` (`cls:<name>` entries): the nearest is the first entry and the root `Entity` is implicitly last. The eid prefix is only the BIRTH DEFAULT: an entity with no `parents` is the list [its eid class] (nothing is stored); an entity BORN with `parents` (a birth by the host, the door or a constructor) gets `cls:<eid class>` put first unless the list names it (a constructor of another class stamps `[cls:<eid class>, cls:<constructor>]`). After the birth the eid class has no standing: a write of `parents` is the whole list, so it can reorder, add or replace classes. A restore reads the stored list as it is (no prefix put back), so a list that dropped the prefix survives a restart; the journal keeps what was said at the birth and the replay renormalises it the same way. `this.cls` reads the first class of the list. Getters of every listed class apply (one rule, below); a kind's setter fires when its class is in the list (no ISA parent entity `cls:<name>` is needed any more; an ISA parent ENTITY further up the chain still counts); a class dropped from the list takes the values its getters wrote with it (cleared, journal-neutral) and a getter node marked before the drop is skipped.
`entity_query kind:<K>` lists an entity by its eid class (the stored row class) or any `parents` kind. A `parents` write on an existing entity computes the getters of its new classes in that round. `instances('<Class>')` lists the same way (the eid class, or a kind in `parents`; for a lazy class the loaded entities only).
Tests: `native/tests/multi_class_1143.rs`, `seat_process.rs` (`an_entity_carries_two_extra_classes...`, through a restart). **One resolution rule** (`resolution_1143.rs`): for each (entity, property) the getters of every class the entity carries form ONE ordered list of arms: the classes of its list (`parents`; the eid class only when there is none), nearest first, then the implicit root `Entity`; within a class the top layer first (`docs/c1f-layers.md`). The first arm whose `WHEN` holds wins, a default (`ELSE:`) ends the search, a failing `WHEN` falls through to the next-nearer class. One node per (entity, property) runs the list (the nearest class's getter; `chain`, `arms_of`, `getters_of` in `fields.rs`). Levels are still ordered per class getter, so a fall-through arm that reads a higher-level getter settles in a later pass of the same round (its reads are its dependencies). The root pack `membrane/packs/entity.c1f` declares `Entity.summary` (the id and the class list; no values). Setters keep their own rule (first write wins), and bind through the same list. Tests: `classlist_1143.rs`.
**The class `Error`** (docs/c1f-error.md item 7, `error_class_1143.rs`): the root pack declares it with one property, `failed` ({property: reason}). While a property of an entity fails the VM keeps `Error` on TOP of its `parents` (derived writes, not journalled; `this.cls` skips it; rule B ignores it) and the reason in `failed[prop]`; a read of such a property is the Error, the getter still recomputes under it, and every success, redefinition or pack removal takes the entry out (the class leaves with the last one). Both are in the stored row, so a restart brings the Errors back. The class entry does not re-resolve the entity's other getters; it wakes what reads the class list (`x is Error`, `instances('Error')`), at most twice per entity per run.

**Retiring an entity** (`native/src/fields.rs` `retired`, `host.rs` `drain_apply`): a write of `retire = true` to ANY entity, by any writer (a pack's setter: the ordinary ownership rules
apply; the model's `entity_write` as the privileged door), removes it: the engine forgets the entity (what read it recalculates), its stored row is deleted. It is derived when a setter wrote it,
so never journalled, and a replay re-derives it; an outside write of `retire` is journalled and replayed like any. Test: `native/tests/host_loop.rs` (retire + replay), `seat_process.rs`.

### The full-set seat (`scripts/seat-full`, #1143)

## The Sql driver: a second SQLite file as entities (#1143, operator 2026-11-14)

`native/src/sqldrv.rs`, `membrane/packs/sql.c1f`, `Help:sql`, tests `native/tests/sql_driver_1143.rs` and `sql_door_1143.rs`. No builtin and no change to `sql()` (which reads the seat's own store): a second
SQLite file (the old store of the migration, the lexicon, a scratch database) is two kinds of entity and one driver verb.
- `SqlSource:<name>` {`path`, `mode`}: `mode` is `ro` (the default) or `rw`. Written by the model with `entity_write` (the owner's tool; the tools pack imports `sql` as it imports `proc` and `fetch`, so the pack
  needs no grant beyond theirs) or pre-declared at launch by the fact `sql_sources`, a LIST `[{name, path, mode}]` (c1f cannot list a dict's keys; `keys()` is only a proposed builtin) that the `sql` pack turns
  into the same entities (the fact SEEDS: a source that already has a path, written by the model or kept from an earlier run, is left alone, so a restart never undoes the model's choice; 2026-11-14, #1143). A `ro` source is opened with SQLite's **immutable** URI (`file:<path>?immutable=1`, read-only, `query_only`): no lock, nothing written beside the file, and **the file must not change while the
  seat runs** (a changed file is read as it was when the source opened, WAL files are ignored: a live database being written is read from a snapshot copy). `rw` opens an existing file read-write. The connection is
  opened lazily by the first run and opened again by the next run after `path` or `mode` was rewritten.
- The seat's OWN store is never a source: a path that resolves to it (canonical path, symlinks, and the same device and inode for hard links) is refused with the reason in the receipt, whoever wrote the path.
- `SqlQuery:<name>` {`source` (the NAME of a SqlSource), `sql`}: the prepared definition. `SqlQuery.run = {id, args: [...], max_rows?}` is a write like `Command.run`: an effect of the slow-driver pool
  (`effect_workers`, `Store::effect_limited`), so a long query never holds the VM. `args` are BOUND parameters, never spliced into the text. The SAME `id` as the entity's latest run (`running.id`) runs nothing (fields.rs
  `driver_effect`); a new `id` runs again. One connection per source, queries on a source serialized (it is locked for the run; a second query on a busy source holds its worker slot while it waits).
- The statement is prepared on first use and kept in the connection's statement cache; the receipt's `prepared` and `reused` count parses and reuses per source (the cache holds `CACHE_STATEMENTS` = 256 texts, one more
  flushes it and the counters stay true; the number is flagged as a decision). A statement that is a read answers its rows; INSERT/UPDATE/DELETE on an `rw` source answer `changes` (`RETURNING` rows too); on a `ro`
  source SQLite refuses the write and its own words are the receipt's `head`.
- The receipt `SqlQuery.run_result` = `{id, status: ok|error, rc, rows: [{column: value}], changes, ms, started, finished, head, prepared, reused, truncated?}` (rc 0 ok, 1 SQLite refused the statement, 2 the run was refused
  before it started: no source, own store, a bad `max_rows`, a file that will not open; a BLOB reads as null). `max_rows` (no default) cuts the rows and says `truncated: true`. Only the LATEST receipt stays on the entity.
  The entity's getters read it (`rows`, `changes`, `ok`, `rc`, `truncated`, `prepared`, `reused`, `status` with `running` in flight); after a failed run `rows`, `ok`, `rc` and `changes` read as `Error` values with the reason, as a
  timed-out `Command` does (`docs/c1f-error.md`), and the Errors clear when a later run succeeds. `SqlSource.opened` reads the open's own receipt (`open_result`, pushed to the source by the driver) and is an Error with the
  reason when the file would not open; rewriting `path` or `mode` makes the old failure stale at once (not an Error again until the next run opens the new file).
- **Replay**: the receipt, rows included, is JOURNALLED (the engine's writer `record:run`, stamped `host:record:run` by `host.rs` `stamp_writer`, the first driver receipt that is an outside write), so a replay (which
  runs no effects) restores the rows and never asks the file again; a restart on the same store reads the rows from the entity's row. Deleting the source file changes neither.
- Native only: the driver is under the `store` feature with the other drivers; the wasm build does not carry it (`wasm_check_1143`).
- Not decided by the build (listed for the operator): a default `max_rows`, the 256-statement cache, whether an `rw` source may create a missing file, the worker slot a busy source holds.

## The host loop (`native/src/host.rs`)

Ported from `membrane/fields_live.py`, the minimum the door and the boot need:

- OUTSIDE writes (a door request born as `Request:<n>`, the boot's facts, a person's write) are heard, journalled, stored and given
  to the engine (a VIRTUAL class's, like `Request` and `Boot`, is only heard: no row, no journal line; "Storage modes" above). A birth from outside goes in as an arrival (`Fields::arrive`: loaded, known, its getters dirty), so a setter on its
  writes fires, as the door always did; the host takes the door's requests itself (`Fields.inbound_by_host`), to journal them.
- The engine's output (`Fields::out`) is drained and applied to the rows with the writer stamped as `fields_live.stamp_writer` /
  `stamp_born_writer`: `trigger:field:<setter>` for the engine's own writes, `host:door` for a request, `host:boot` for the boot.
- The clock: `Fields::tick` every second; the loop wakes at once when a driver thread finishes (query, file, command, request).
- The JOURNAL holds the outside writes only. Derived writes are never in it: replay re-derives them
  (`Host::replay`). The journal is kept in memory and in `c_journal`.
- Test (`native/tests/host_loop.rs`): a live run (door requests) is replayed into a fresh engine and
  store and gives the same entities and rows (values and writers), and the same journal. A driver's receipt (`*_result`, `*_rc`) is
  an effect's answer and is not re-derived: a replay runs no effects, so the comparison leaves those props out.
- Process tests (`native/tests/cliffvm_process.rs`): the built binary on an ephemeral port serves a static file, boots through the
  real plan and answers a decisions route and a 501 route, stops on SIGTERM (hard timeouts, the child is always killed).

## Pack entities: the model loads its own packs (design, 2026-11-13)

- A **Pack** is an entity `Pack:<name>` whose `text` property holds c1f. The model writes it with the tool it already has:
  `entity_write {spec: 'Pack:mine', prop: 'text', value: '<c1f>'}`. No new tool, no new syntax. The name is what follows `Pack:`.
- Writing `text` loads (or replaces) the pack at once through `Fields::set_pack(name, text)`: its classes, getters and setters are live
  for the next write. Writing `text` to none or empty removes it (`remove_pack`; an entity is removed by the `retire` write).
- The host mirrors the outcome back as DERIVED writes (`trigger:field:pack`, never journalled): `loaded` (true when the pack is active),
  `error` (the loader's message, absent when fine) and `good_text` (the last text that loaded). The text write itself is the model's
  write (a Request's setter in the MCP door) and is replayed, so a replay loads the same packs in the same order.
- A refused text keeps the previous pack running: `set_pack` parses and checks (stale setter reads) BEFORE it replaces anything, and an
  import problem restores the old one. A refusal sets `error`; `loaded` stays what the running pack is. Restart: the packs folder loads
  first, then every stored `Pack:*` row (name order) from its `text`, falling back to `good_text` when the text is refused.
- The name and the text's `PACK` line: `set_pack` refuses a text whose `PACK <name>` line names another pack, so the id wins by
  refusal (the line is optional; the message says what it found). The same as `fields_live`.
- A Pack that imports a pack that is not there yet WAITS (kept, inactive) and activates when the import arrives; its `error` says
  what it waits for (Python leaves `error` empty for that and only for view packs waiting for `dom`; here the model needs to see it).
- Packs from the FOLDER stay files: loaded once at start, not entities, not reloaded. A Pack entity of the same name replaces the
  file's pack (it loads later).

**How the model loads a pack (as built).** One `entity_write {spec: "Pack:mine", prop: "text", value: "<c1f>"}`; read `Pack:mine.state`
(`loaded` / `error` / `waiting`) or `.error`. Rules the engine puts on what the pack can do:
- A class a pack declares is OWNED by it (rule A: only the owner defines its getters and setters; others IMPORT). A pack may WRITE only
  classes it owns or imports (rule B), unless it is PRIVILEGED (docs/c1f-layers.md, "Privilege"). `door_tools`, the pack behind the
  model's `entity_write`, is privileged: boot.c1f grants it at start (`Pack:door_tools.privileged = True`, `granted_by` records the boot
  setter). So the model's tool writes AND creates an entity of any class, including one a model-written pack owns:
  `entity_write {spec: "Lamp:desk", prop: "power", value: "on"}` makes `Lamp:desk` and its setters and getters run. No roundabout needed
  (the old way, a setter on the pack's own `Pack.mode` that makes the Lamp, still works). An UNPRIVILEGED pack (the model's packs are
  not, unless a privileged writer grants it with `entity_write {spec: "Pack:mine", prop: "privileged", value: true}`) is still held to
  rule B, and cannot write `privileged` at all (a setter, constructor, computed name or chain of setters: refused with a receipt).
- A pack that is removed (text emptied, or the Pack entity's text none) stops running and the values its getters left on entities are
  CLEARED (derived writes of none, journal-neutral; a property another pack still computes stays). A Pack entity with NO text (a grant
  for a pack loaded from a FILE) never removes that pack; only a written empty text does.
- The engine's rounds apply: a setter that writes the same property twice in one round is refused (`refused` on the entity).
- Test: `native/tests/pack_entities.rs` (the binary, the MCP door: load, hot reload, parse refusal, stale-setter refusal, PACK-line
  refusal, restart with a broken text falling back to `good_text`), `native/tests/host_loop.rs` (outside writes, journal, replay,
  removal, a pack waiting for an import), `native/tests/privilege_1143.rs` (rule B, grant, revoke, granted_by, cleanup, replay) and the two
  direct-write tests in `pack_entities.rs`.

## Eval accounting: `Stats:eval` (#1143)

Which getters and setters burn the time is a question the VM answers about itself (`native/src/stats.rs`). Always on (the boot fact `eval_stats`, default on; `--fact eval_stats=false` turns it off and there is no entity), the VM counts per **(kind, class, property, pack)** the evaluations, their **self time** (the run's own clock time, minus what it waited in host calls such as `sql(...)`, which is counted apart as `wait_ms`, minus the runs nested in it) and their **steps**. The table is a fixed `Vec` (2048 slots, 1024 keys; a key past that is counted in one `(other)` row); counting a known key allocates nothing.

The host publishes it on the entity `Stats:eval` (class `Stats`, RESIDENT, declared by the shipped pack `stats`, in `barest.packs`) every window (`--fact eval_stats_window_s=<s>`, default 10; a threshold flagged for the operator): `window_s`, `top` (the top 20 of THIS window by self time: `{class, prop, pack, kind, calls, ms, wait_ms, steps, slow}` (`slow` = the evaluations whose own self time passed the former 10 ms allowance, `MEMBRANE_EVAL_TIME_MS`: a flag, never a limit; time decides no value, docs/c1f-stdlib.md)), `total_calls`, `total_ms` (all rows of the window), `top_total` (the same top over the process's lifetime), `life_calls`, `life_ms`, `at`. The writes are the host's (`host:stats`), heard by the engine but **not journalled** (like an unload: not part of a replay); no pack reads the entity, so nothing reacts. `Stats:eval.reset = true` clears the table at the next tick and lowers the flag. Read it with `entity_read` or `run_cliff` (`Stats:eval.top`). The counting changes no value; its cost is about 125 ns per evaluation (`overhead_report` in `native/tests/eval_stats_1143.rs`, a report, not an assertion). A rebuild (start-up) evaluates a getter once, then only those whose inputs a write of the previous pass changed (a getter whose inputs did not move is not evaluated again; before, a chain that never settled ran every getter of every entity up to 16 times: `Command.timeout_default` 1890 evaluations for 189 Commands, now 378). Tests: `eval_stats_1143.rs`, `eval_stats_host_1143.rs`, `seat_process.rs` (`stats_eval_...`, `the_boot_fact_eval_stats_false_...`).

## What `fields_live.py` does that the Rust loop does NOT yet do

- **Mirroring the Python entity store**: there is none here; the rows are the host's own table. No `est.docs` hear/mirror, no
  `mirrored()` by ISA kinds (`parents: ["cls:..."]`), no class-of-removal memory, no mirrored removal of entities (`f.remove`, #1054; the `retire` write, see the barest seat, does it for the engine and the store): on the barest seat the engine collects every virtual entity nothing holds (a Request included); elsewhere a
  Request entity stays forever.
- **`silent_birth`** on engine-born entities (`{"born": cls}` is stored with no props).
- **Packs from entities, the rest**: `pack_op` (list/show/load), the shipped-pack rule, `_view_classes` (packs importing `dom` that
  run in pages), `Pack` entities with the Python name `membrane::pack:<name>` / a `c1f` property / any class holding c1f (here only
  `Pack:<name>.text`, see "Pack entities"; the privilege grant is the one other Pack property the host reads, `privileged`). Pack FILES are loaded once at start: no mtime rescan. A Pack
  entity can not be deleted (its text emptied removes the pack). Entities other than Packs are restored by `load_stored_entities` (see "Restart restores the entities").
- **Banner instances per owner and chat** (the barest seat has the one `Banner:owner:main`: see "The banner"), the dials (`recall:dials`), the class switch (writing `class` does not reassign an instance), facts per turn, `sql_forget`,
  the 3 s banner time limit, `mark_delivered` / `mark_seq`.
- **LLM call plumbing**: `Fields::calls` (the planner's `membrane::llm.call`) are drained and dropped; no LLM adapter.
- **Host callbacks** (`_Host.call`: `pronoun`, `recall`, `rerank`, the banner's built-ins): `NullHost` knows none; `resolve`,
  `dispatch`, `vel`, `align`, `live` answer nothing.
- **Adapters**, the worker pool, wait checks, replan, Blurp's learner and the store's write listeners that watch writes.
- **Presence**, peers, the `/event` hub (`publish` of `field.write` / `field.pack` / `field.remove` to pages), the browser VM's
  snapshot (`snapshot()`), the page feed.
- **Seat facts**: `seat_facts` reads the person's settings file, the router, the minds, the backend, cloud models,
  `agent_writes`, `nerve_pause_off`, `ledger`, `router_on`, `minds`, `seat_stt`, `seat_project`; the binary tells only the list above.
  `answer_card` (the board's own door) is a pack's now, but nothing calls it here.
- **The store as the seat's**: no `Store:field` seed entity, no `SQL_ARRIVED` queue item (the loop's waiter does that job), no
  `set_store` of a seat file other than its own; the seat's collections (`c_<coll>` of the Python entity store) are not the host's
  table (`c_field`): the two do not read each other.
- **Plan state is not journalled**: `plan::set` writes engine-side (writer `boot`); a boot re-runs the plan each start.
- **Error handling**: a failing write does not count `errors`, nothing is logged per write; a pack that fails to load is printed
  once on stderr and the last good one is not kept.
- **Shutdown**: SIGTERM stops the loop and interrupts running queries; there is no flush beyond SQLite's own, no `stop(srv)`.

## The barest agent seat: the MCP door and the chat (#1143, operator 2026-11-12)

The app is packs only: `door_tools.c1f` (the model's tools), `chat.c1f` (the one chat), `chat_turn.c1f` (the turn). Rust added
only three small things: a write with a computed property name (`<target>.[expr] = v`, `fields.rs`), the kind getters of a constructed
entity (a kind stamp came after the birth), and `cliffvm run ... --fact name=value` (any Boot fact, JSON or text). Run it with the
shipped packs (`boot fs proc fetch store door door_tools chat chat_turn`) plus the barest app folder (its `default_banner.c1f` births the banner) and
`--fact chat_claude_bin=<path to the claude CLI>` (no default: without it a message is answered with an error and nothing runs).

**Routes** (no persons, no auth, one chat `membrane::Chat:main`):
- `POST /mcp`: MCP over plain HTTP, JSON-RPC 2.0, one JSON answer per request: `initialize` (echoes the client's `protocolVersion`, else
  2025-03-26), `notifications/*` and any request with no id (202, no body), `ping`, `tools/list`, `tools/call`; `-32700` / `-32600` / `-32601`
  errors; a GET is a 405 (`allow: POST`: there is no SSE stream). The tools are the FIELD ops only, nothing else:
  - `entity_query {q, k, count}`: `kind:<Class>` and `name~:<eid prefix>` joined by `&` (anything else is a tool error), rows `eid (Class)`,
    k default 20 at most 100; reads the store's rows (`c_field`).
  - `entity_read {spec, prop}`: the stored properties of an entity, or one property in full (a getter's value too).
  - A Fetch receipt carries `started`, `finished` (epoch seconds) and `ms` like a Command's, on a refusal too (`drivers.rs`).
  - A chat turn whose CLI ended badly keeps its cause: `ChatTurn.error` and the response say the stage (`claude failed (rc N): <stderr>`, `ended without an exit code (killed by a signal ...)`, `ended with no answer at all`, the output unreadable); a turn whose stream gave a result line is never marked error for an unreadable stream (`chat_turn.c1f`: `rlines`, `finals`, `evl`).
  - `entity_write {spec, prop, value}`: one property, by a computed-name write; what reacts runs (a setter, a driver verb such as
    `Command:x.run = {id, args}`); the receipt is read back as `<verb>_result`. The class must be one `door_tools` owns or imports
    (door, fs, proc, fetch, store) or one no pack owns yet; a refusal is in the reply. A write to an entity that does not exist and whose
    class no pack owns is dropped by the engine (the reply cannot tell: read it back). `door_tools` is PRIVILEGED (granted by boot.c1f
    at start), so it is not held to that class rule: it writes and creates any class, including one a model's pack owns.

**The event stream** (#1143; `native/src/http.rs`, `drivers.rs`, `membrane/packs/door.c1f`, `chat.c1f`, `chat_turn.c1f`; tests `host_loop.rs`, `chat_process.rs`).
Three pieces, all writes (no host callback):
- *A Request can answer open-ended.* `Request.stream = {id, status?, headers?}` writes the head of a `text/event-stream` response (default `Content-Type`,
  `Cache-Control: no-store`, no length, `Connection: close`) and keeps the connection; `Request.send = {id, event?, data}` appends one event
  (`event: <event>` when named, `data: <data as one line of JSON>`, a blank line); `Request.end = {id}` closes. A route asks for it with a reply
  `{status: 200, stream: True}` (the door's `answer-stream` setter writes `stream`; a reply without `stream` is still `respond`). The frames are queued on the
  engine's thread in write order, and the effect threads write them, so two sends never swap. Receipts: `stream_result`/`send_result`/`end_result`
  (`rc` 0, or 1 when the client went away, or 2 when there is no open stream); a failed write forgets the stream. No keep-alive comment and no write timeout
  (thresholds, not chosen).
- *A Command can deliver while it runs.* `Command.run = {id, args, partial: True}` pushes each read's complete lines of stdout (the unterminated tail at
  the end) as an outside birth `Chunk:<command eid>:<n>` ({cmd, id, n, data}), in the style of `Fetch`'s chunks: a VIRTUAL class, so never stored or journalled (what was derived from them while the turn ran is not needed again: the receipt is the answer); the receipt still carries the whole `stdout`. A run without `partial` makes none. An arriving entity now marks the readers of
  its class (`instances('Chunk')` recalculates), which a door request did not need until now.
- *The chat turn uses both.* The turn runs with `partial: True`; `ChatMessage.partial_text` (the `text_delta`s of the `stream_event` lines) and `partial_tools` (the
  `tool_use` blocks started) read ONE accumulator chunk, `Chunk:<command eid>:acc` (`text`, `tools`): each chunk parses its own lines (`Chunk.part`) and its setter `partial-in` appends them there, so a birth costs the same whatever came before (the old `ChatMessage.chunks` getter listed every live chunk at each birth: a turn of N chunks cost N squared; test `the_work_per_chunk_does_not_grow_with_the_chunks_already_born`); `ChatMessage.stream_view` is the view with those while the turn runs. The chunks and the accumulator are collected once the turn's command has ended (the command's in-flight effect holds them while it runs; after its receipt they are held by nothing: "Garbage collection of virtual entities").
`GET /membrane/chat/message/<id>/events`: 404 `{error}` for an unknown message; otherwise 200, then one event `message` per change of `stream_view`, whose data
is `{id, text, state (queued | running | done | error), response (the partial answer while running, null until a word is out; the final one when done), tools
(names; the final list when done), turn: {state, started, ended}}`. Events are snapshots (a missed one costs nothing), the last is the one with `state` done or
error, then the connection closes. The stream's `Request` is held by its open connection while the stream is open: it is collected only
after `end_result` (or a failed `stream`); a client that leaves early makes the next send fail, and the turn's own `end` still lands. The page (`chat.js`) opens an
`EventSource` for a running message and polls it again only if the stream errors; `graph.js`/`app.js` still poll (3 s, hidden tab skipped): the graph needs a stream of
its own later (not built).

*Ids* follow the Python seat's `<prefix>_` and 24 digits, derived from the message so no table is kept: a session `ses_<ms:13><request n:8>000`, a message's rows `msg_<ms><n>001` (user) and `...002` (assistant), parts `prt_...010` (the user's text), `...100` (the answer's text part), `...2jj` (tool j of the turn); events `evt_...`. Limits that follow: a request number above 99,999,999 and more than 100 tools in one turn. *Parts of the assistant row*: finished, the tools the model ran in call order (`tool` parts, `completed`, with input and output; the part's `time` is the turn's), then ONE text part, the CLI's final answer (the lead-in words the model wrote between tool calls are streamed but not stored: the row is rebuilt from the entities, `ChatMessage.oc_parts`); running, what the stream has shown so far. A failed turn is the error text as its text part and `info.error {name: Error, data: {message}}`; an aborted one `MessageAbortedError`. `info` carries `tokens` and `cost` of the CLI's result line.
*The event streams*: `Request.send` takes `{id, frames: [{event?, data}, ...]}` (several frames in one write, queued in order). The engine allows ONE write of a (entity, property) in a cascade (a second is refused: "loop: ... already written this round"), except a driver verb (`send`, `run`, ...): a command, one effect per write, run in write order. So each producer writes its OWN bus entity (`SesBus:start-<id>`, `SesBus:chunk-<id>-<n>`, `SesBus:end-<id>`: virtual entities, a list of `{type, id, properties}`), a chunk of the CLI's output and the turn's end can land in one round without one dropping the other, and the bus's setter writes the frames to every open stream (`Request.ev_on`), wrapped for `/global/event`. A chunk taken after its turn is over says nothing (the end's final parts carry the words). Three producers: the message's start (`queued`: user message and part, `session.updated`, busy, the assistant's message, `session.updated`), each chunk of the CLI's output (`Chunk.oc_go`: the answer's words, the text part opened EMPTY with the first, then a `message.part.delta` per read; a tool's part `running` when it starts and `completed` when its result line comes, up to 8 per read), and the turn's end (`ChatMessage.oc_fin`: the final parts with the SAME ids, so the page's rows are replaced, the message completed, `session.status` idle, `session.idle`, `session.updated`). A stream that opens later sees only what follows (`server.connected` first); the page loads the rows after it connects. Differences from the Python seat: no `session.diff`, no step parts, no keep-alive ping, no `membrane.*` events; the lead-in text of a turn is one text part while it streams and the final answer replaces it; inside one read of the CLI's output the words come before the tools; a turn REFUSED before it started (no `chat_claude_bin`) ends in the start's own cascade, so its end is not on the stream (the rows and `/session/status` have it).
*The shape comparer* (`session_1143.rs`, `shape_misses`): the answers are compared with the Python seat's recorded answers (`scripts/golden_session.py --tree <v0.7.53 checked out>`; no model, the turn runner's ladder is a stub): every key of the fixture in the answer with the same JSON type, extra keys allowed, a `null` in the fixture accepts any type, each element of an answer's list matches SOME element of the fixture's list; values (ids, times) are never compared. `tests/js/page_boot.test.mjs` shows the page itself (headless Chrome) creating a session and following `/ui/serve/event`.

## Open design questions

1. **Effects on replay.** A driver receipt is outside in nature (a connection answered, a file read) but stamped derived
   (`trigger:field:driver:*`) by the python rule. Replay here runs no effects and the comparison ignores receipts. Should receipts
   be journalled (outside), or should replay run the effects again? (Answered for the Sql driver, 2026-11-14: its receipts are journalled, writer `record:`.)
2. **Who owns the entity rows.** The Python seat's store is the `EntityStore` over `db.rs` (a pyclass); the host has its own table.
   Converging needs `db.rs`'s core split from its Python binding (a refactor, not done).
3. **Request entities**: the engine collects them once nothing holds them (a seat built from the Python packs, which the engine also runs, keeps its own).

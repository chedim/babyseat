# cliffvm: the seat's program (developer and operator reference)

Status: describes `cliffvm` 0.7.63 (`native/`, `membrane/packs/`, `membrane/apps/barest.c1f/`). Every claim was checked against the code or a test named next to it. The Python seat is gone (its source is the tag `python-seat-last`);
Python is only the pip wrapper (`membrane/launcher.py`) and the Home Assistant component. The user-facing page is the README; auth is docs/auth.md. Items still in progress are marked with the branch that carries them.

`cliffvm` is the cliffhanger field VM as a process of its own: no Python, no pyo3. `cliffvm --version` prints `cliffvm 0.7.63`
(the `version` of `native/Cargo.toml`, the one number of the release: pyproject, the Home Assistant manifest and the dist folder's `VERSION` carry the same). `cliffvm --help` prints the usage;
`cliffvm serve --help` the launcher's options. The command name lives in ONE place, the `[[bin]] name` in `native/Cargo.toml`.

**The door is strict and there are no users** (docs/auth.md). `cliffvm serve` makes a door secret and an admin token in the data folder; every route but the page's shell needs a verified token and every verified token is the
admin. The door opens on 127.0.0.1 unless `--bind` says another address. A door with NO secret (`--fact door_secret_file=` on `serve`, or `cliffvm run` without the fact) is open and every caller is the admin: for tests only.

**The app is a folder of packs (or a pack file).** `main()` parses arguments into Boot facts and runs the apps given; every route, tool, turn and view is a `.c1f` pack in one (the shipped `membrane/packs/*.c1f` and
`membrane/apps/barest.c1f` are the app). Several apps are LAYERS and the FIRST is the root of trust (docs/c1f-layers.md). The Rust side is only the host: the loop, the drivers, the store, the socket.
A decision a pack could make is not made in Rust: if it shows up, it is listed below.

## Build and run

```
cd native
cargo build --release --no-default-features --features bin     # target/release/cliffvm
cliffvm --version
cliffvm serve [options]                                        # the users' launcher
cliffvm run <app> [<app>...] [--store <sqlite>] [--port <n>] [--bind <addr>] [--ui-dir <dir>] [--fact name=value ...]   # the low-level command
cliffvm token mint --sub <id> --ttl <30d|12h|15m|45s|seconds> --secret-file <path> [--name <name>]
```

- Features (`native/Cargo.toml`): `store` = rusqlite + tls (the native store, the drivers, the door); `bin = [store]` (the app; the default, so a plain `cargo build --release` builds it); `wasm` (the browser engine, `native/build-web.sh`, `scripts/build_wasm.sh`);
  `metal` (a GPU path of the vector search, macOS); `alloc-stats` (a diagnostic); `tls` (https for Fetch). The app's flags `--no-default-features --features bin` still work and are what the suites use (`cargo test --release --no-default-features --features bin`).
- `run <app>...`: an APP is a folder `<name>.c1f/` or one pack file (the loader tells them apart). The `.c1f` files of a folder (its whole tree) are packs, loaded in dependency order (a pack after the packs of that app it imports;
  of those ready, the alphabetically first path next); every other file is DATA at its path (the door serves an app's `ui/` files). Several apps load in the order given and each is a layer above the one before it:
  a pack whose name is already loaded is skipped (the lower layer's stays). **Trust is by position, never by name**: the packs of the FIRST argument are the root of trust (privileged: docs/c1f-layers.md, "Privilege");
  a later app has no privilege until a privileged pack grants it (`Pack:<name>.privileged = true`; boot.c1f grants `door_tools`). A pack named `boot` in a later app is not trusted.
  The boot plan (`boot.json`, `boot.c1f`) is looked for beside the first app. After the packs: the getters are computed once (a rebuild runs no setter), the boot plan runs, the facts are told, then `Boot.started`, then the loop runs until SIGTERM/SIGINT.
  `--port` becomes the fact `door_port` (0 = any free port); the pack `door.c1f` answers with `Http:door.listen`; once it is up the binary prints `cliffvm: door listening on <host>:<port>`. The door binds 127.0.0.1 unless `--bind` says otherwise.
- Facts the arguments tell (names as `membrane/packs/facts.json`; `native/src/cli.rs` `facts`): `door_port`, `ui_dir`, `app_dirs` (the folders of the apps given, the upper layer first; the door serves each one's `ui/` files, an upper layer's
  file shadowing the lower's), `seat_version`, `build_id` (`cliffvm-<version>`), `seat_cwd`, `seat_home`, `anthropic_key_set` (yes or no, never the key), `seat_name`, `seat_named`, `seat_aliases`, `seat_voice_out`, `seat_language`,
  `seat_blurp` (always false), and the whole set as the dict `facts`. Then `--fact name=value` (JSON when the value parses, else text) wins over the seat defaults (`seat_name` Bob, `seat_named`, `seat_aliases`, `seat_voice_out`, `seat_language`, `seat_blurp`), not over the host's own facts (`seat_version`, `build_id`, `seat_cwd`, `seat_home`, `anthropic_key_set`).
- `--store`: one SQLite file (default `./cliffvm.sqlite3` for `run`, `<data-dir>/seat.sqlite` for `serve`), WAL: the entity rows (`c_field`: eid -> {cls, props, writers}), the journal (`c_journal`), and what `sql(...)` in packs reads
  (read-only connections of the same process). The WAL is folded back and truncated by the clock tick once it is over `WAL_LIMIT_BYTES` (8 MB, `host.rs` `trim_wal`; test `native/tests/wal_1143.rs`). The main file does not shrink after rows are retired
  (freed pages are reused, `auto_vacuum` is off). DURABILITY: the store is WAL with `PRAGMA synchronous = NORMAL` (`Host::open`): a commit is not fsynced one by one, so a power loss (not a process crash) may lose the last commits, never corrupts the file;
  a clean restart keeps everything (test `finished_guard_1143.rs`).
- The boot plan: this host runs none of the plan's steps, so each is `skipped` and the plan only says when the boot is over. Then `started`.

**Every entity remembers what birthed it** (#1143, operator 2026-11-14; `vm.rs` `BORN_BY`, `Core::born_by`): `<entity>.born_by` is a VM-provided, read-only property like `updated`: the eid of the CAUSE of the birth, the entity whose setter was running when the entity was made (the setter's `this`; for a door `entity_write` that creates its target, the call's `Request`; for a cascade, the entity of the step that did the birth). An entity with no cause (loaded at start, born by the host) reads as the plain `absent` null. It is a constant: set once, stored with the row (one string `born_by` in the body, no key when there is none; it survives the VM's eviction and a restart) and never written (a setter's write is refused with a receipt, an outside write is dropped and not journalled), so a getter that reads it is only recomputed when the entity itself arrives. A birth a replay recomputes gets the same cause; a birth it cannot (a virtual trigger's, journalled as an outside birth) carries it in the journal line's optional `by` (a journal without it replays as no cause). **The VM rule `births_to`** (`vm.rs` `BIRTHS_TO`, `Fields::cause_of`): when the entity whose setter creates an entity has a property `births_to` holding a non-empty entity id, the created entity's `born_by` is that id instead of the setter's own entity (an ordinary property read at the birth; no other effect). The door uses it for the turn's link: the turn's MCP config carries `X-Turn: <the message's id>` (`chat_turn.c1f` `mcp_server`), `Request.mc_message` (`door_tools.c1f`) is that header when it names an existing chat message, and `Request.births_to` is the message or else the Request itself; `run_cliff` copies it to the scratch entity whose setter runs the block. So what a door call creates says the MESSAGE in `born_by`, permanently (the Request is collected after its reply, the message is not), and "which entities did this message create" is `[x.eid for x in instances('<Class>') if x.born_by == '<message>']`; a call with no message header (or one naming no chat message) says its Request. Tests: `native/tests/born_by_1143.rs` (including `births_to`, replay and restart), `native/tests/born_by_chain_1143.rs`.

**A command's input** (#1143, operator 2026-11-14): the run value may carry `stdin` (text): `Command:x.run = {id, cmd, stdin: "..."}`. The child gets a piped standard input; the driver writes the text on its own thread (a big text cannot deadlock against the output pipes the driver reads) and then CLOSES the pipe, so a program that reads to the end of its input proceeds. Without `stdin` the child's stdin is null (end of input at once), as before. The text is part of the request like `args`: it is in the run write, which the journal records like any write (the chat turn's banner and message were already in the argv, so nothing new is exposed), and it is not a place for secrets (those go by `env_from`). Tests: `command_stdin_1143.rs`.

**A command's time limit** (`drivers.rs`, `proc.c1f`; operator request 2026-11-13, after a model-run `grep -r` over the whole projects tree ran 71 minutes and held a worker slot): `timeout_s` is the model's own estimate of the longest a command may run, in the run value
(`Command:x.run = {id, cmd, timeout_s: 600}`) or set on the entity before the run. Without it the Boot fact `command_timeout_s` applies (default 120 s, the operator-delegated sensible default).
There is no upper bound and no unbounded command: 0 or less (or a non-number) is refused with a reasoned receipt, a long job states a big number. The child leads its own process group; at the deadline the group gets SIGTERM, after `KILL_GRACE_MS` (2 s) SIGKILL;
the worker slot is freed when the run ends. The receipt: `status: "timeout"`, `rc: 124` (the convention of GNU `timeout`), `killed: true`, `timeout_s`, `ms`, the partial stdout/stderr (the reply's 8 KB head/tail rules apply); a run in time carries `timeout_s` too
and no `killed`. The receipt is the journalled outside write like any driver receipt: a replay runs nothing, so there is no clock in it. `Command.stop` kills the same group at once. A timed-out run's `output`, `errors`, `ok` and `rc` are REASONED NULLS
(`why(Command:x.output)` = `Command:x timed out after N s (killed); start it again with a bigger timeout_s, e.g. run = {id, cmd, timeout_s: 600}`; getters built on them pass the null and the reason on); `partial_output` / `partial_errors` hold what was read, `run_rc` stays the raw 124.
The write reply says the same in a `timeout:` line; the pending reply shows `timeout_s` and the seconds `left`; `running` = {id, started, timeout_s}. The chat turn's own `claude` run states `timeout_s` = `chat_turn_timeout_s` (default 21600 = 6 h, a threshold flagged for the operator), so the default never kills a turn.

**`run_cliff`** (#1143; `door_tools.c1f` `cl_*`, `help/cliff.md`): the fourth MCP tool, next to entity_query / entity_read / entity_write (none removed). A CLIFFLET is a small block of the getter-body syntax (locals, the last line is the value) run in one call. Built from existing parts:
the door writes TWO scratch Pack entities at once, `cliffg<n>` (the block as the body of a getter `val`, plus `shown` = `{v: val, why: why(val)}`) and `cliffs<n>` (the block as an on-setter body `go`; privileged, so a block may write any class like `entity_write`,
imports door/fs/proc/fetch/store), each with a class of its own (`Cliffg<n>`, `Cliffs<n>`). Both packs carry `scratch = true`: `instances(<Class>)` does not list an entity with `scratch = true`, so a block listing `instances('Pack')` sees the field's packs, the same set as `entity_query kind:Pack`, not its own scaffolding (an explicit property, not a name rule; test `a_clifflet_reads_eid_cls_and_parents_and_lists_the_same_packs_as_entity_query`). `eid`, `cls` and `parents` read in a block as they do on any entity (`chat_process.rs` `a_clifflet_reads_eid_cls_and_parents...`). Whichever loads decides the mode: a block that loads as a getter is a VALUE (the scratch entity `Cliffg<n>:x` is born by a write and `shown` is read); one that loads only as a setter body is WRITES
(`Cliffs<n>:x.go = True`, with `mc_done` so the host tells back the reactions of the round exactly like `entity_write`, `reactions_of` accepts the setter `cliff-run`); one that loads as neither answers `the block did not load.` with both loader messages. The value comes back as text (`str`: JSON for a list or dict, a plain
null is `null`), a null with a reason as `null: <reason>` (`isError` false: nothing failed) and a failure (an Error) as `Error: <reason>` (`isError`), so a runaway block answers `Error: budget exceeded (N steps)` under the engine's step budget (100,000 steps by default, `MEMBRANE_EVAL_BUDGET` overrides: docs/c1f-stdlib.md, "Limits") (time limits nothing, so a slow block still answers its value) and the seat goes on. The size of the answer is not capped. A write that starts an effect has its receipt in a later round (`<verb>_result`). After the answer the setter
`cliff-finish` stores it (`cl_final`) and retires the scratch entity and both packs (the pack text is emptied, then retired). Tests: `chat_process.rs` (`a_clifflet_reads_and_joins...`, `a_clifflet_that_writes...`, `a_runaway_clifflet...`: 20 calls of four shapes leave the entity count and the pack count as they were); `help_1143.rs` runs every ```cliff / ```cliff-write block of `Help:cliff`.
Costs: loading a pack (a cliff call loads and removes one) recomputes only the getters the load changed or added; a getter the new set carries unchanged keeps its value and its inputs, and the getters of one property name count as changed together (they stack their arms; `Fields::set_getters`, test `idle_getters_1143.rs`; before, every getter of every entity was evaluated again, `Command.timeout_default` about 90 times a second on a seat with ~200 commands and a model calling `run_cliff`). **Storage modes** (#1143, operator 2026-11-13; `native/tests/storage_1143.rs`, `lazy_boot_1143.rs`): a class has one of three modes, declared by the pack that OWNS the class in its header, one class per line, like `IMPORT`
(`docs/c1f-layers.md`, "Header lines"). The mode is by the entity's own class (its eid's; `membrane::Chat:message:1` is `Chat`):

| mode | header line | stored | loaded | journalled | `entity_query` |
|---|---|---|---|---|---|
| virtual | `VIRTUAL <Class>` | no row | RAM only, never restored | no | no (it is not a row) |
| resident | `RESIDENT <Class>` | yes | ALWAYS: at start, and the moment a pack declares it | yes (outside writes) | yes |
| (default) lazy | none | yes | ON DEMAND, see below | yes | yes |

- **MAPPED** (`MAPPED <Class> <dtype>`, #1143, operator 2026-11-14; `native/tests/vector_1143.rs`, `native/src/vecstore.rs`): a fourth, narrower mode for a class whose entities carry ONE big list of numbers, the property `v`. The class stays lazy (its row is stored,
  loaded on demand, unloaded under memory pressure like any), but `v` lives in a native store, one flat f16 matrix per class (the dtype is declared so another is a header change; `f16` is the only one, another name is refused when the pack loads). The shipped class
  is `Vector` (`membrane/packs/vector.c1f`). A write of a list of numbers to `Vector:<id>.v` stores it (the row keeps the text `[1024 numbers, f16]`, so `entity_read` without a property and `entity_query` with `full` or `props` print that, and `entity_read` with `prop: v` prints the numbers: the existing
  "one property in full" read); a rule reads `v` as a list of floats (the f16 value decoded) and calls `near(list, 'Vector', k)` (`docs/c1f-stdlib.md`). The dimension is fixed by the first vector written to the class (until the class is empty again); another length, a non-number or a value out of the f16 range is REFUSED with
  a receipt on the entity (`refused`). The journal keeps an outside write of `v` COMPACT (`{"$f16": "<base64 of the f16 bytes>"}`, ~2.7 KB for 1024 numbers, not ~20 KB of JSON floats), so a replay restores the same f16 values; a write of the same values again is a no-op. Persistence: the table `c_vectors` (eid, class, bytes) of the seat's
  SQLite store, loaded at open into the in-memory matrix; a retired entity (and its colon-path children) deletes its row and swap-removes its matrix row (no tombstones, nothing to compact); clearing `v` (a null) does the same for that vector. SIZE: the matrix is `rows x dimension x 2` bytes in RAM (1,000 vectors of 1024 numbers: about 2 MB; 20,000: about 41 MB), the same again in the file.
  The memory policy (`evict_under_pressure`) evicts entity ROWS only: the vector store is not an entity row and is never evicted by it. The browser engine has no store: a write of `v` is refused and `near` answers that it is not available there.
  **A MAPPED class's entities are journalled whole, even what a rule writes** (#1143, operator 2026-11-14; `host.rs` `mapped_stamp`). A vector is usually made by a rule from a Fetch receipt (the embedding), and a receipt is derived and NOT journalled
  (a body of 1,024 floats is ~14 KB of JSON a vector, ~0.9 MB for a batch of 64), so a replay of the journal alone, with no drivers, would make no vectors. So the birth and every property write (`of`, `start`, `v`, ...) of an entity of a MAPPED class
  is stamped `host:mapped:<setter>`, an OUTSIDE write, with `v` in the compact form: about 3.2 KB a vector in all (birth, three props, `v` ~2.7 KB), ~4 times less than the receipt; the RAM copy of the journal keeps only a size for the `v` line.
  A getter's value (`Vector.dim`) stays derived (a replay computes it). Only MAPPED classes: every other derived write and every driver's receipt (Fetch, Command, File, Store) stays derived. A replay applies the lines as outside writes (a replay of the
  same lines twice changes nothing: a write of the same value is a no-op).
  **`MAPPED <Class> f16 derived`** (#1143, 2026-11-15, a language-surface change AWAITING THE OPERATOR'S APPROVAL; `vecstore::DERIVED`, `Core::is_mapped_journalled`, `native/tests/mapped_derived_1143.rs`): the third word turns the rule above off for that class. What a RULE writes to its
  entities (the birth, `v`, every other property) stays a DERIVED write like any other class's: stored in the row and the vector table, restored at a restart (the rows and `c_vectors` are the state), and NOT journalled. An outside write is journalled as before (compact).
  So a replay of the journal alone does not rebuild such a class: it is for state a pack computes from other stored state and keeps as rows, never recomputes at start (the field's states, seeds, episodes and background, `membrane/packs/field.c1f`).
- **Shipped declarations** (the header lines of the packs: `grep -h '^VIRTUAL\|^RESIDENT\|^MAPPED' membrane/packs/*.c1f membrane/apps/barest.c1f/*.c1f` lists them). VIRTUAL: `Request`, `Return`, `Chunk`, `Step`, `Span`, `SesBus`, `Page`, `LinkPeer`, `FvDir`, `FvFile`, `FieldStep`, and `Boot` and `Http` (see "What `PER_RUN_CLASSES` did").
  MAPPED: `Vector`; `derived`: `FieldSeed` (the vector pack), `FieldState`, `FieldEpisode`, `FieldBg` (the field pack, `membrane/packs/field.c1f`). RESIDENT: `Pack`, `Banner`, `Help`, `Command`, `File`, `Dir`, `Fetch`, `Store`, `SqlSource`, `SqlQuery`, `Environment`, `Stats`, `Embed`, `Legacy`, the goal graph's `Goal`, `Task`, `Wait`, `Decision` (`native/packs/goalgraph.c1f`), and every class a pack lists whole with `instances(...)` (`Attention`, `Model`, `Minds`, `Intent`, `Seat`, `Ctx`, `Tool`, `Message`, `Setting`, ...) or whose driver is a sensor (`Peer`, `McpServer`).
  Everything else is lazy (`Chat` and its messages, turns, responses and tools). A test lists every `instances('X')` in the shipped packs and refuses one whose class is not declared (`a_class_a_pack_lists_with_instances_is_loaded_whole_or_is_virtual`). Only the owner declares a mode (a storage line claims a
  class no pack owns yet); a class cannot be both; a refusal names the pack that owns the class and what it declares.
- **VIRTUAL semantics.** Never stored (`store_born`/`store_prop` skip it), never restored, never journalled (`journal_push` skips a line about it). The engine keeps it, so a getter, a setter, `instances`, `prop(<id>, ...)` and a block run by `run_cliff` read the LIVE ones;
  `entity_query` and `entity_read` without a `prop` read the store and do not see them. What a setter writes to a stored entity while a virtual one triggers it (a chat message born by a setter on a `Request`) could not be derived again by a replay (its trigger is not in the journal),
  so the host stamps it `host:virtual:<setter>`, an OUTSIDE write: journalled with its time, and a replay of the journal ends in the same state. Only the first hop is stamped: what that write's own setters and getters make is derived again by the replay.
- **LAZY LOAD** (`Core::unloaded`: eid -> class, noted at start from a covering index on `(cls, k)`: no body is read). A stored entity loads on its first REFERENCE: a read by id or entity literal from a getter, a setter, a block or the door tools (the evaluation finds nothing, the engine loads the row at once and evaluates again,
  `Core::fault_now`); a write (an outside one, or a setter's: `Fields::ensure` before the target is looked for, so a setter never makes an entity that is stored); `Host::get`. A loaded row brings its stored properties (a getter's stored value too: the read is right away), its getters recompute (the stored value stands until they do) and what read its fields or listed its class recalculates.
  **`instances('<Class>')` lists the entities whose eid class is `<Class>` AND those that carry it as a kind in their `parents` list (`instances('ChatMessage')` lists the messages, whose eid class is `Chat`); for a LAZY class only the entities that are LOADED** (a class that was never referenced since the start may list none); a RESIDENT class lists all of them, a VIRTUAL one all the live ones. `referencing(x, 'prop')` likewise sees only loaded referrers. A getter that must see every
  stored entity of a class declares the class RESIDENT, or asks the store (`sql(...)`: the barest `Boot.interrupted` finds the turns a run left `running` that way; a `sql` getter's answer is cached, so it is a start-up read). Door tools `entity_query` and `entity_read` (no `prop`) read the store: complete, whatever is loaded.
  `instances` walks the loaded entities once per class: the sorted answer is kept per class (lower-cased) until an entity THAT CAN BE IN IT arrives, leaves, changes its class or writes `parents` / `scratch` (`Core::inst_touch`; a `Request` being born no longer drops `instances('Boot')`; walks are counted, `Host::inst_scans`), and the class test reads the `parents` entries without building a list (`Ent::in_classes`). Before, every call walked 30,000-60,000 loaded entities building a list of Strings each (3-5 ms a call, eight calls a request: a request for one row cost 80 ms with a big session loaded, 29 ms now; `native/tests/instances_cost_1143.rs`, which counts walks).
  A retired entity takes its stored, unloaded children (`A:1:x` under `A:1`) with it. A runtime pack that declares a class RESIDENT loads its stored rows at once. An entity can also leave the engine again: "Eager unload" below.
- **WARM BOOT.** At start the host loads the packs, then the RESIDENT rows (restore rules as before: a getter's stored value is not read back, the rebuild computes it again), notes the rest, and the loop serves: the door answers at once. In the BACKGROUND, between turns of the loop, the newest-`updated`
  unloaded rows load, `WARM_SLICE_ROWS` (64) or `WARM_SLICE_MS` (20 ms) at a time, up to the boot fact `warm_rows` (`--fact warm_rows=<n>`; default `DEFAULT_WARM_ROWS` = 1000; 0 = none). The three numbers are thresholds, flagged for the operator.
  Numbers (release build, synthetic Note rows of ~250 bytes, one machine): 5,000 rows: door up in 0.67 s / 56 MB before, 0.12 s / 15 MB after; 50,000 rows: 6.8 s / 388 MB before, 0.33 s / 26 MB after; a copy of the real repro store (470 rows, 18 MB): 4.5 s / 184 MB before, 0.37 s / 40 MB at the door (72 MB after the warm boot).
- **`updated`** (a VM-provided, READ-ONLY property of every entity): the epoch time of the entity's last write. The host stamps it with the write, in the same row and transaction (`c_field.updated`, indexed; next to it `cls`, indexed: the restore loads the resident classes by it). No extra write, no reaction (a setter on `updated` never fires), no getter recompute (a getter that read
  it keeps what it read until something else it reads changes); a setter that writes it is refused (a receipt), an outside write of it is dropped (not journalled). Derived writes take the time of the outside write that started their round, so a replay (which applies the journal's recorded times) ends with the same `updated`. A virtual entity has it too (RAM).
  Read it as `<entity>.updated` from a block or a getter, or `entity_read {spec, prop: 'updated'}`. A store of an older shape is migrated at open: the columns are added, `cls` is filled from the body, `updated` from the journal's last line about each entity (0 when the journal never names it: only outside writes are journalled); once, never over a later stamp.
- **EAGER UNLOAD** (#1143, operator 2026-11-13; policy moved into the engine 2026-11-14; `native/tests/unload_1143.rs`, `unload_process_1143.rs`): the opposite of lazy load. An entity not touched for a while leaves the engine, its row kept, and the next reference loads it again (the lazy path above). **The VM does it by itself: no pack, no write, nothing a pack or the model can name** (operator, 2026-11-14: "the model does not maintain what is in memory, the VM does"). A property called `unload` is ordinary data with no behaviour: a write of it is stored and read back like any other, evicts nothing and gets no receipt. Eviction is not journalled (a replay never sees it) and changes no value.
  - **The facts** (`memory_budget_mb`, `unload_soft`, `unload_hard` (fractions of the budget), `unload_batch`): a fact the operator names is used as given. The launcher's default (operator 2026-11-14, `MemoryConfig::with_defaults`) fills what is left unnamed: the budget is 10% of the machine's memory (a container's lower limit counts as the machine), `unload_hard` 0.9 of the budget, `unload_batch` 200, no soft line. On a machine whose memory cannot be read nothing is added and nothing is ever evicted. The effective values are told as facts too, so the settings window shows them.
  - **The policy** (`Host::evict_under_pressure`, `host.rs`), run at the end of every drain (so inside a long cascade too, like the history import), only while a budget and a batch are set. Pressure = the resident size at or over `unload_hard` x budget (the budget itself when unset) or at or over `unload_soft` x budget (no soft line when unset). Under pressure ONE pass: the `unload_batch` COLDEST loaded entities leave, coldest = the smallest touch clock, i.e. the least recently read, written or loaded. Candidates: only stored entities that may leave; never a RESIDENT or VIRTUAL class (packs, drivers, whatever a pack lists whole), never one with a running effect (`running` set), never one a live VIRTUAL entity holds by a `$ref` (a request still being answered holds what it points at). The rows are written first, then the whole batch goes with ONE pass over the field's bookkeeping (`Fields::unload_many`: the entity, its place in the load order, its own getters' read lists, the engine's memory of its last evaluations). The resident size is `process_rss()` (`task_info(MACH_TASK_BASIC_INFO)` on macOS, `/proc/self/statm` on Linux; nothing on other targets: no eviction there). TEST ONLY: `MEMBRANE_TEST_RSS=<file holding the size in bytes>` replaces the reading (`cli.rs`; an unreadable file falls back to the real one), or `Host::set_rss_reading` in-process.
  - **What this means for a bulk writer** (the history import): rows nobody reads back are the coldest once newer ones arrive, and one drain evicts at most `unload_batch`, so the loaded count stays bounded when the batch is at least what one cascade creates; with no budget set nothing is evicted and the import keeps everything it wrote in memory.
    **What depends on an unloaded entity** (the simple SAFE rule): nothing is marked dirty and nothing recomputes. A getter that read it keeps its cached value (an unload changes no value); when that getter next recomputes and reads the entity, the read loads it again (`Core::fault_now`), and an arrival makes the readers of its fields recompute as any load does. A write to it loads it first (`Fields::ensure`). So a dependency never sees a hole, and an entity that is read all the time is hot, hence never among the coldest. A cached `instances('<lazy class>')` keeps naming an unloaded entity until it recomputes; `instances` and `referencing` list only what is loaded (documented above).
  - **The touch clock** (`.touched`, `Ent::touched`, `Core::clock`): a counter in the core bumps at every read of a stored property (an evaluation's attribute read), every write that reaches the entity and its load; the entity keeps the counter's value. RAM only, never stored, never journalled. `.touched` is read-only and VM-provided like `.updated`; reading `.touched`, `.updated`, `.eid`, `.cls` or `.pinned` touches nothing. The entity's reads by the door's store-reading tools (`entity_query`, `entity_read` without a `prop`) do not touch it: they do not read the engine. **Exception**: an entity that STORES a property named `touched` (`Turn.touched` of `turn.c1f`, a pack the release does not load) reads its own: the clock does not shadow a stored value, and a setter that writes `touched` writes that property. The cost: a counter increment and two `Cell` stores per read, 0.56 ns measured (release build, `unload_1143.rs` `the_cost_of_the_touch_clock_per_read`, run by hand with `--ignored`), against about 255 ns for a whole evaluation of `this.n`.
  - Complexity: a pass is O(loaded entities) (a partial selection of the `unload_batch` coldest), once per drain while the process is over a line; an unload is O(its own getters and dependency edges), and the batch's pin check builds the set of `$ref` targets of the live virtual entities once per pass. The load order keeps a hole per removed entity and closes them when they outnumber the live ones (amortised O(1)), so load/unload cycles do not grow it.
  - **Flagged**: soft and hard run the same pass (a choice the operator may change); the pass runs per drain, not per second.
  - Tests: `unload_1143.rs` (touch clock, `unload` is plain data for a person and for a pack, the pressure loop with an injected resident size and lazy reload of every value, no budget / no batch / no soft, the pins, restart, replay), `unload_process_1143.rs` (the binary with `MEMBRANE_TEST_RSS`), `legacy_cutover_1143.rs` (the import bounded by the policy).

- **GARBAGE COLLECTION OF VIRTUAL ENTITIES** (#1143, operator 2026-11-13; `native/tests/gc_1143.rs`, `chat_process.rs` `a_request_is_collected_right_after_its_reply_...`): a virtual entity (`Request`, `Return`, `Chunk`, `Step`, `Boot`, `Http`) is collected at the END OF THE ROUND in which nothing holds it any more. No pack retires it (`Host::drain_apply` runs the collector last, `Core::gc_dead`; removing the dead is a round of its own, as a retire is, and drains again). Only VIRTUAL classes: a stored entity keeps its explicit `retire` and the unload above.
  **Holders.** (1) OWNERSHIP: a colon-path child lives while its parent ENTITY lives (`Request:7:body` with `Request:7`; the parent of `a:b:c` is `a:b`, and it must be an entity). (2) A REFERENCE: a live entity has the virtual entity's id as a `{"$ref": "<id>"}` value in a property, at any depth (a list, a dict). That is the form the engine already stores an entity VALUE in (`V::Ent`), so a setter writes `this.keep = Req:made` (or `[Req:made]`), a getter that returns an entity (or a dict or list holding one) holds it, and `x = None` releases. The engine keeps a reverse index of these values per (holder, property), current on every write, load and removal (`Core::ref_in`; the cost per write is one lookup and a walk of the new value). A held `wait` reply holds its Request through its open connection.

What holds is a VALUE that is stored. **Roots**: every non-virtual loaded entity, packs, the drivers' in-flight work, and the host's own: `Boot:seat` (`Host::hold`, called by `boot_started`) and the boot plan's steps (`Core::host_held`). A loop of virtual entities that hold each other and nothing else is unreachable: both are collected (`Core::held` walks the holders of an entity with a visited set; it finds a root or it does not).
  **When, and what it costs.** A candidate is an entity born this round, or one that lost a holder (a reference written away, a holder collected, a holder removed), or one whose effect receipt the engine took this round (and then the live entities that name it as their owner). Only candidates are looked at: no scan of the field per round. A candidate costs the length of the chain of holders it walks (usually 1; a Request is held by its connection at once); an effect's end costs one pass over the LIVE virtual entities (`Core::virt_live`) to find the ones that name it; a dead entity releases what it held and its colon-path children, and the pass goes on until nothing new dies.
  **A read of a collected entity** is a null with the reason `collected: nothing held it` (`V::Nil`, as `why(...)` reads it); the last `COLLECTED_KEPT` (4096, flagged) ids are remembered for that, older ones read as a plain missing entity. Writing to a collected entity is dropped as a write to any missing one. A Request that the client abandoned before the pack answered is held by its connection forever (as it always was); an answered one is gone with its reply.
  **What it replaced** (the barest app's `collector.c1f`, `door_tools.c1f`, `chat_turn.c1f`): `Request.answered`, `Request.expired`, `dropped`, `kept_at`, `keep_s` and the retire writes for Request; the Return's setter-based retire (`mcp-return-retire`, `mc_w_sent`, `mc_w_ret`: the Request now HOLDS its Return by reference, `mc_w_returned` is `Return:call:<n>` as a value, so the Return goes with its Request); the chat turn's `stale_chunks` + `retire-chunks` (the Chunk is held by the Command's in-flight effect; once its receipt is taken nothing holds it). `collector.c1f` keeps ONLY the start-up sweep of the stored Request rows an older run left (they are stored text). The fact `request_keep_s` is still ACCEPTED (`--fact request_keep_s=<n>`; the launch lines that pass it do not break) and does nothing: no pack reads it.
  **An entity that holds a live virtual one is never evicted** (it is pinned, `.pinned` says so): evicting it would drop the reference and the virtual entity would be collected under whoever still wants it.

**What `PER_RUN_CLASSES` did.** The old list (`Boot`, `Http`, `Request`, `Step`) kept those classes out of a restart: their rows were stored text and the new run made them again. Its job is `VIRTUAL` now, and those four are declared VIRTUAL (`boot.c1f`, `door.c1f`): the restore skips them as before, and
a row an older run stored stays text (the collector's start-up sweep still retires old `Request` rows). Two things differ for `Boot` and `Http`, which were stored and journalled: they are no longer rows (`entity_query kind:Boot` is empty; `entity_read Boot:seat` with a `prop` still reads the live entity), and the boot facts are not in the journal, so what the

**Restart restores the entities** (`host.rs` `load_stored_entities`, called by `cli.rs` after `load_stored_packs` and before the rebuild): the stored `Pack` rows first, then the RESIDENT classes' rows arrive in the engine with their class and props
(the `parents` stamp is a prop); every other row of a lazy class is only noted and loads on reference or in the warm boot (above). A prop a getter wrote (`trigger:field:getter:*`, `rebuild`) is not read back for a resident row: the rebuild computes it again, so a changed getter shows its new value. A VIRTUAL class's row is skipped. No setter runs on a restore and nothing is rewritten.
A turn that was `running` when the seat stopped (its Command had no receipt) is marked `error` at start, with the response `interrupted: the seat stopped while this turn was running` (the words the model had streamed are not stored while a turn runs, so none are kept; only a Stop keeps them, on `kept`) (`chat_turn.c1f`, `Boot.interrupted`: a `sql` over the store's running turns that started before this run's `Boot.started`; the turns are lazy, so the engine's `instances` cannot be asked).

**An entity of several classes: the class list** (#1143): an entity has NO privileged own class. Its classes are ONE ordered list, its `parents` (`cls:<name>` entries): the nearest is the first entry and the root `Entity` is implicitly last. The eid prefix is only the BIRTH DEFAULT: an entity with no `parents` is the list [its eid class] (nothing is stored); an entity BORN with `parents` (a birth by the host, the door or a constructor) gets `cls:<eid class>` put first unless the list names it (a constructor of another class stamps `[cls:<eid class>, cls:<constructor>]`). After the birth the eid class has no standing: a write of `parents` is the whole list, so it can reorder, add or replace classes. A restore reads the stored list as it is (no prefix put back), so a list that dropped the prefix survives a restart; the journal keeps what was said at the birth and the replay renormalises it the same way. `this.cls` reads the first class of the list. Getters of every listed class apply (one rule, below); a kind's setter fires when its class is in the list (no ISA parent entity `cls:<name>` is needed any more; an ISA parent ENTITY further up the chain still counts); a class dropped from the list takes the values its getters wrote with it (cleared, journal-neutral) and a getter node marked before the drop is skipped.
**`parents` is hidden from the model**: `entity_read` and `entity_query` leave it out of their rows (and show a failed property as `Error: <reason>`), the reactions of a write leave it out, `entity_write` refuses to write it (`door_tools.c1f`; classes are set at birth with a constructor and tested with `x is Class`); a pack or a `run_cliff` block can still read and write it.
`entity_query kind:<K>` lists an entity by its eid class (the stored row class) or any `parents` kind. A `parents` write on an existing entity computes the getters of its new classes in that round. `instances('<Class>')` lists the same way (the eid class, or a kind in `parents`; for a lazy class the loaded entities only).
Tests: `native/tests/multi_class_1143.rs`, `seat_process.rs` (`an_entity_carries_two_extra_classes...`, through a restart). **One resolution rule** (`resolution_1143.rs`): for each (entity, property) the getters of every class the entity carries form ONE ordered list of arms: the classes of its list (`parents`; the eid class only when there is none), nearest first, then the implicit root `Entity`; within a class the top layer first (`docs/c1f-layers.md`). The first arm whose `WHEN` holds wins, a default (`ELSE:`) ends the search, a failing `WHEN` falls through to the next-nearer class. One node per (entity, property) runs the list (the nearest class's getter; `chain`, `arms_of`, `getters_of` in `fields.rs`). Levels are still ordered per class getter, so a fall-through arm that reads a higher-level getter settles in a later pass of the same round (its reads are its dependencies). The root pack `membrane/packs/entity.c1f` declares `Entity.summary` (the id and the class list; no values). Setters keep their own rule (first write wins), and bind through the same list. Tests: `classlist_1143.rs`.
**The class `Error`** (docs/c1f-error.md item 7, `error_class_1143.rs`): the root pack declares it with one property, `failed` ({property: reason}). While a property of an entity fails the VM keeps `Error` on TOP of its `parents` (derived writes, not journalled; `this.cls` skips it; rule B ignores it) and the reason in `failed[prop]`; a read of such a property is the Error, the getter still recomputes under it, and every success, redefinition or pack removal takes the entry out (the class leaves with the last one). Both are in the stored row, so a restart brings the Errors back. The class entry does not re-resolve the entity's other getters; it wakes what reads the class list (`x is Error`, `instances('Error')`), at most twice per entity per run.

**Death by null** (operator, 2026-11-14): `<entity> = None` in a setter (and an outside write of a plain null to an entity with no property, `Host::write(eid, "", null)`; the tool `entity_write {spec, value: null}` with no prop) is `retire = true` on it, the mirror of a birth (`fields.rs` `kill`). ONLY a plain `None` destroys: a reasoned null, an Error or a non-null value is refused with a receipt and nothing is destroyed; ownership rules unchanged, no class guard. A retired `Pack:<name>` also unloads the pack (`remove_pack_clean`, the layer below shows again) and the reply says `pack <name> unloaded`. The page's JS host needs no change (the engine still emits `retire = true`), only the wasm core is rebuilt to know the syntax.

**Retiring an entity** (`native/src/fields.rs` `retired`, `host.rs` `drain_apply`): death by null above is the way to say it, and it comes down to this: a write of `retire = true` (which a pack or a block may still write directly) to ANY entity, by any writer (a pack's setter: the ordinary ownership rules
apply; the model's `entity_write` as the privileged door), removes it: the engine forgets the entity (what read it recalculates), its stored row is deleted. It is derived when a setter wrote it,
so never journalled, and a replay re-derives it; an outside write of `retire` is journalled and replayed like any. Test: `native/tests/host_loop.rs` (retire + replay), `seat_process.rs`. In the BROWSER VM the host does the same (`membrane/apps/barest.c1f/ui/fieldvm.js` `retire`, #1143): the entity leaves the page's engine and a DomNode's element leaves the page (`tests/js/fieldvm_retire.test.mjs`); the page has no store, so there is no row.

## The edit pack: a hunk applied by a write (`membrane/packs/edit.c1f`)

A change to a file as data, in plain c1f over the fs stdlib (no builtin, no Rust). `Edit:<name> {path, old, new, base_mtime}` is one hunk: `old` has to occur in the file
exactly once. Writing `apply = {id}` checks it and writes the file with an ordinary `File.write` (the effect is `File:edit:<name>`, whose receipt wakes the edit, which reads the
file again); writing `revert = {id}` puts the pre-image back. Reads: `problem` (why the hunk cannot be applied now: no path, empty `old`, no `new`, no such file, not found, matches N
times, changed since), `diff` (`- old` / `+ new`), `hits`, `status` (`draft ready pending applied reverted refused failed`), `refused` (the last refusal's reason), `text`, `info`, `pre`, `post`.
A draft changes nothing, so reading `diff` and `problem` is the dry run. The lock is optimistic: `base_mtime` is the `mtime` of `info` as the agent read it, and another mtime at apply
is a refusal; a revert is refused when the file is no longer `post`. `apply` and `revert` are two steps, because a read lands later: the write sets `want` and a fresh `seen` token, so the file is read again, and the setter on `snap` checks the hunk
against that fresh text and stat and then writes (status `pending` in between), so the checks and the lock never run on a cached read; use a new `id` for every apply. Tests: `native/tests/edit_pack.rs`
(real files, mutation-checked); the model reads `Help:edit`.

## The Sql driver: a second SQLite file as entities (#1143, operator 2026-11-14)

`native/src/sqldrv.rs`, `membrane/packs/sql.c1f`, `Help:sql`, tests `native/tests/sql_driver_1143.rs` and `sql_door_1143.rs`. No builtin and no change to `sql()` (which reads the seat's own store): a second
SQLite file (the old store of the migration, the lexicon, a scratch database) is two kinds of entity and one driver verb.
- `SqlSource:<name>` {`path`, `mode`}: `mode` is `ro` (the default) or `rw`. Written by the model with `entity_write` (the admin's tool; the tools pack imports `sql` as it imports `proc` and `fetch`, so the pack
  needs no grant beyond theirs) or pre-declared at launch by the fact `sql_sources`, a LIST `[{name, path, mode}]` (`keys(d)` lists a dict's keys, in order) that the `sql` pack turns
  into the same entities (the fact SEEDS: a source that already has a path, written by the model or kept from an earlier run, is left alone, so a restart never undoes the model's choice; 2026-11-14, #1143). A `ro` source is opened with SQLite's **immutable** URI (`file:<path>?immutable=1`, read-only, `query_only`): no lock, nothing written beside the file, and **the file must not change while the
  seat runs** (a changed file is read as it was when the source opened, WAL files are ignored: a live database being written is read from a snapshot copy). `rw` opens an existing file read-write. The connection is
  opened lazily by the first run and opened again by the next run after `path` or `mode` was rewritten.
- The seat's OWN store is never a source: a path that resolves to it (canonical path, symlinks, and the same device and inode for hard links) is refused with the reason in the receipt, whoever wrote the path.
- `SqlQuery:<name>` {`source` (the NAME of a SqlSource), `sql`}: the prepared definition. `SqlQuery.run = {id, args: [...], max_rows?}` is a write like `Command.run`: an effect of the slow-driver pool
  (`effect_workers`, `Store::effect_limited`), so a long query never holds the VM. `args` are BOUND parameters, never spliced into the text. The SAME `id` as the entity's latest run (`running.id`) runs nothing (fields.rs
  `driver_effect`); a new `id` runs again. One connection per source, queries on a source serialized (it is locked for the run; a second query on a busy source holds its worker slot while it waits).
- The statement is prepared on first use and kept in the connection's statement cache; the receipt's `prepared` and `reused` count parses and reuses per source (the cache holds `CACHE_STATEMENTS` = 256 texts, one more
  flushes it and the counters stay true; the number is flagged as a decision). A statement that is a read answers its rows; INSERT/UPDATE/DELETE on an `rw` source answer `changes` (`RETURNING` rows too); on a `ro`
  source SQLite refuses the write and its own words are the receipt's `head`.
- The receipt `SqlQuery.run_result` = `{id, status: ok|error, rc, rows: [{column: value}], changes, ms, started, finished, head, prepared, reused, truncated?}` (rc 0 ok, 1 SQLite refused the statement, 2 the run was refused
  before it started: no source, own store, a bad `max_rows`, a file that will not open; a BLOB reads as null). `max_rows` (no default) cuts the rows and says `truncated: true`. Only the LATEST receipt stays on the entity.
  The entity's getters read it (`rows`, `changes`, `ok`, `rc`, `truncated`, `prepared`, `reused`, `status` with `running` in flight); after a failed run `rows`, `ok`, `rc` and `changes` read as `Error` values with the reason, as a
  timed-out `Command` does (`docs/c1f-error.md`), and the Errors clear when a later run succeeds. `SqlSource.opened` reads the open's own receipt (`open_result`, pushed to the source by the driver) and is an Error with the
  reason when the file would not open; rewriting `path` or `mode` makes the old failure stale at once (not an Error again until the next run opens the new file).
- **Replay**: the receipt, rows included, is JOURNALLED (the engine's writer `record:run`, stamped `host:record:run` by `host.rs` `stamp_writer`, the first driver receipt that is an outside write), so a replay (which
  runs no effects) restores the rows and never asks the file again; a restart on the same store reads the rows from the entity's row. Deleting the source file changes neither.
- Native only: the driver is under the `store` feature with the other drivers; the wasm build does not carry it (`wasm_check_1143`).
- Not decided by the build (listed for the operator): a default `max_rows`, the 256-statement cache, whether an `rw` source may create a missing file, the worker slot a busy source holds.

## The Cron driver: a schedule as an entity (#1143, operator 2026-11-16)

`Cron:<name> {schedule, enabled}` (`membrane/packs/cron.c1f`, RESIDENT, in `membrane/apps/barest.packs`; tests `native/tests/cron_1143.rs`, on a fake clock in a fixed zone, nothing sleeps). The pack does everything that is logic; the Rust is ONE verb and a timer table.

- **Syntax.** Standard 5-field cron `minute hour day-of-month month day-of-week` (lists `1,2`, ranges `1-5`, steps `*/5` and `10-40/10`, `*`; numbers only, day-of-week 0-7 with 0 and 7 Sunday; both day fields restricted: a day matches if EITHER does, as cron always did), or `@every <n><unit>`, the unit `s m h d`, n a whole number above 0. Wall time is the seat's local zone (`localtime`, `native/src/clock.rs`). Cron fields are minute-granular; `@every 1s` is the smallest tick. A schedule that cannot be read is REFUSED, never guessed: the getter `problem` is the reason (a text, else null), `next` is null and nothing is armed (bad field, wrong field count, unknown `@` form, a date that never comes such as `0 0 31 2 *`).
- **The flow.** A setter (`cron-schedule`, `cron-enabled`, and `cron-boot` on `Boot.started` for every Cron) writes `base = clock`; the getter `nx` is the plan from it, the first matching minute STRICTLY after (the search is c1f: the minute-of-day list `tod`, then the first matching local day among the next 62, else among days 63-1462, about 4 years: a 29 February is found, a date that never comes is `problem`); the setter on `nx` writes `due` and the driver verb `Cron.arm = {id, at}`. The driver arms ONE timer per entity (a second `arm` replaces it; `at: null` disarms; `enabled: false`, a refused schedule and a rewritten `schedule` all go this way). `next` reads `due`, `last` reads `fired.at`.
- **The driver** (`drivers.rs` `("Cron", "arm")`, `store.rs` `arm_timer` / `fire_due`): no thread. The timers sit in a table of the store; the host loop (`Host::pump`) asks `fire_due(now)` with ITS clock, and each timer whose time has come answers like any effect with the receipt `arm_result = {id, status, rc, at, fired}` (`at`: the time it was armed for; `fired`: the clock that woke it). The receipt is the one outside write: `fields.rs` gives a `Cron:` receipt the writer `record:arm` (stamped `host:record:arm`, the same as the Sql receipts), so it is JOURNALLED once. An armed entity counts as in flight (the collector and the memory policy leave it). The wake is as precise as the host loop's turn (it turns at least every 50 ms).
- **The event.** The pack's setter on `arm_result` writes `fired = {id, at}` and plans from `at`; anything reacts with an ordinary setter on `Cron.fired` (`Help:c1f`, "Cron"). Because the next timer is armed only after the receipt was handled, a fire can never overlap the handling of the one before it.
- **Late wakes are dropped, not queued.** When the plan from the slot that fired is already in the past (the engine was busy longer than a slot) the slots are SKIPPED and counted in `dropped` (for `@every` the number of intervals skipped; for cron fields 1 per late wake), and the plan restarts from now (`late = {for, at}`: the engine refuses a second write of `base` in one cascade, so the re-plan has its own property). The `@every` grid is kept (`at` + k * n).
- **Restart.** The timers are RAM; a restore runs no setter, so `cron-boot` plans every Cron from the clock of the start: the missed runs are SKIPPED (not caught up, not counted), the next one is armed. **Replay** runs no driver (no store, no timer): the journalled `arm_result` lines re-derive `fired`, `due`, `dropped` and what a setter on `fired` did, and nothing fires again.
- **Not covered / open.** Daylight-saving transitions are not tested (the zone offset is read at the local noon of the target day, so a fire inside the hour of a transition may be an hour off); the real clock is exercised by the host loop only, never by the tests; `dropped` for cron fields is 1 per late wake, not the number of matching minutes skipped; no month or day names (`jan`, `mon`), no `@daily`.

## The host loop (`native/src/host.rs`)

The minimum the door and the boot need:

- OUTSIDE writes (a door request born as `Request:<n>`, the boot's facts, a person's write) are heard, journalled, stored and given
  to the engine (a VIRTUAL class's, like `Request` and `Boot`, is only heard: no row, no journal line; "Storage modes" above). A birth from outside goes in as an arrival (`Fields::arrive`: loaded, known, its getters dirty), so a setter on its
  writes fires, as the door always did; the host takes the door's requests itself (`Fields.inbound_by_host`), to journal them.
- The engine's output (`Fields::out`) is drained and applied to the rows with the writer stamped by `host.rs` `stamp_writer` /
  `stamp_born_writer`: `trigger:field:<setter>` for the engine's own writes, `host:door` for a request, `host:boot` for the boot.
- The clock: `Fields::tick` every second; the loop wakes at once when a driver thread finishes (query, file, command, request).
- The JOURNAL holds the outside writes only. Derived writes are never in it: replay re-derives them
  (`Host::replay`). The journal is kept in memory and in `c_journal`.
- Test (`native/tests/host_loop.rs`): a live run (door requests) is replayed into a fresh engine and
  store and gives the same entities and rows (values and writers), and the same journal. A driver's receipt (`*_result`, `*_rc`) is
  an effect's answer and is not re-derived: a replay runs no effects, so the comparison leaves those props out.
- Process tests (`native/tests/cliffvm_process.rs`): the built binary on an ephemeral port serves a static file, boots through the
  real plan and answers a decisions route and a 501 route, stops on SIGTERM (hard timeouts, the child is always killed).

## Pack entities: the model loads its own packs (design, 2026-11-13)

- A **Pack** is an entity `Pack:<name>` whose `text` property holds c1f. The model writes it with the tool it already has:
  `entity_write {spec: 'Pack:mine', prop: 'text', value: '<c1f>'}`. No new tool, no new syntax. The name is what follows `Pack:`.
- Writing `text` loads (or replaces) the pack at once through `Fields::set_pack(name, text)`: its classes, getters and setters are live
  for the next write. Writing `text` to none or empty removes it (`remove_pack`; an entity is removed by the `retire` write).
- The host mirrors the outcome back as DERIVED writes (`trigger:field:pack`, never journalled): `loaded` (true when the pack is active),
  `error` (the loader's message, absent when fine) and `good_text` (the last text that loaded). The text write itself is the model's
  write (a Request's setter in the MCP door) and is replayed, so a replay loads the same packs in the same order.
- A refused text keeps the previous pack running: `set_pack` parses and checks (stale setter reads) BEFORE it replaces anything, and an
  import problem restores the old one. A refusal sets `error`; `loaded` stays what the running pack is. Restart: the packs folder loads
  first, then every stored `Pack:*` row (name order) from its `text`, falling back to `good_text` when the text is refused.
- The name and the text's `PACK` line: `set_pack` refuses a text whose `PACK <name>` line names another pack, so the id wins by
  refusal (the line is optional; the message says what it found).
- A Pack that imports a pack that is not there yet WAITS (kept, inactive) and activates when the import arrives; its `error` says
  what it waits for (the model needs to see it).
- Packs from the FOLDER stay files: loaded once at start, not entities, not reloaded. A Pack entity of the same name replaces the
  file's pack (it loads later).

**How the model loads a pack (as built).** One `entity_write {spec: "Pack:mine", prop: "text", value: "<c1f>"}`; read `Pack:mine.state`
(`loaded` / `error` / `waiting`) or `.error`. Rules the engine puts on what the pack can do:
- A class a pack declares is OWNED by it (rule A: only the owner defines its getters and setters; others IMPORT). A pack may WRITE only
  classes it owns or imports (rule B), unless it is PRIVILEGED (docs/c1f-layers.md, "Privilege"). `door_tools`, the pack behind the
  model's `entity_write`, is privileged: boot.c1f grants it at start (`Pack:door_tools.privileged = True`, `granted_by` records the boot
  setter). So the model's tool writes AND creates an entity of any class, including one a model-written pack owns:
  `entity_write {spec: "Lamp:desk", prop: "power", value: "on"}` makes `Lamp:desk` and its setters and getters run. No roundabout needed
  (the old way, a setter on the pack's own `Pack.mode` that makes the Lamp, still works). An UNPRIVILEGED pack (the model's packs are
  not, unless a privileged writer grants it with `entity_write {spec: "Pack:mine", prop: "privileged", value: true}`) is still held to
  rule B, and cannot write `privileged` at all (a setter, constructor, computed name or chain of setters: refused with a receipt).
- A pack that is removed (text emptied, or the Pack entity's text none) stops running and the values its getters left on entities are
  CLEARED (derived writes of none, journal-neutral; a property another pack still computes stays). A Pack entity with NO text (a grant
  for a pack loaded from a FILE) never removes that pack; only a written empty text does.
- The engine's rounds apply: a setter that writes the same property twice in one round is refused (`refused` on the entity).

## The environment: `Environment:host` (#1143, operator 2026-11-14)

At the start the host (`host.rs` `boot_environment`, one call in `cli.rs` `run`, before `started`) writes ONE entity, `Environment:host`, whose PROPERTIES ARE the environment variables (property name = variable name; unset = absent, a reasoned null). Class `Environment`,
declared RESIDENT by `membrane/packs/environment.c1f` (a pack of the barest set: without it the write would be dropped, and a host with no such pack writes nothing). It is STORED and written by a JOURNALLED outside write (`host:environment`): a replay of a run's
journal gives the value the boot saw; a restart rewrites it (a variable no longer set is cleared). THE SECRET RULE (docs/auth.md): only the default names (`HOME`, `USER`, `LANG`, `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `TMPDIR`, `CLAUDE_BIN`, `MEMBRANE_DATA_DIR`) and those of the
fact `env_allow` carry their value; a name holding KEY, TOKEN, SECRET, PASSWORD, PASSWD or CREDENTIAL (any case) reads the text `set` when set and non-empty, never its value, and `env_allow` refuses such a name (said on stderr, no value); every other variable is absent. Help: `Help:environment`.
Tests: `environment_host_1143.rs`, `environment_process_1143.rs` (the real binary; the secret values are searched in every reply, the store, WAL, journal, stdout, stderr and `ps`). The history cutover reads `Environment:host.MEMBRANE_DATA_DIR` (`legacy_cutover.c1f`).
Journal across restarts: the stored journal (`c_journal`) holds ALL outside writes, in order, across restarts: the line key continues from the highest stored key at open (`Host::open` reads `MAX(k)`, one index lookup; the in-memory `journal` copy holds only this run's lines). Before this the key was the in-memory count, restarting at 0, so a restart replaced the earlier run's first lines and a replay lost the births. The journal now only grows (an idle restart of the barest seat adds about 8 lines, 1 KB; the first boot is about 400 lines, 60 KB); nothing replays it at startup (the rows of `c_field` are the state), only `migrate`'s one-time `updated` backfill reads it. Test: `journal_restart_1143.rs`.

## Eval accounting: `Stats:eval` (#1143)

Which getters and setters burn the time is a question the VM answers about itself (`native/src/stats.rs`). Always on (the boot fact `eval_stats`, default on; `--fact eval_stats=false` turns it off and there is no entity), the VM counts per **(kind, class, property, pack)** the evaluations, their **self time** (the run's own clock time, minus what it waited in host calls such as `sql(...)`, which is counted apart as `wait_ms`, minus the runs nested in it) and their **steps**. The table is a fixed `Vec` (2048 slots, 1024 keys; a key past that is counted in one `(other)` row); counting a known key allocates nothing.

The host publishes it on the entity `Stats:eval` (class `Stats`, RESIDENT, declared by the shipped pack `stats`, in `barest.packs`) every window (`--fact eval_stats_window_s=<s>`, default 10; a threshold flagged for the operator): `window_s`, `top` (the top 20 of THIS window by self time: `{class, prop, pack, kind, calls, ms, wait_ms, steps, slow}` (`slow` = the evaluations whose own self time passed the former 10 ms allowance, `MEMBRANE_EVAL_TIME_MS`: a flag, never a limit; time decides no value, docs/c1f-stdlib.md)), `total_calls`, `total_ms` (all rows of the window), `top_total` (the same top over the process's lifetime), `life_calls`, `life_ms`, `at`. The writes are the host's (`host:stats`), heard by the engine but **not journalled** (like an unload: not part of a replay); no pack reads the entity, so nothing reacts. `Stats:eval.reset = true` clears the table at the next tick and lowers the flag. Read it with `entity_read` or `run_cliff` (`Stats:eval.top`). The counting changes no value; its cost is about 125 ns per evaluation (`overhead_report` in `native/tests/eval_stats_1143.rs`, a report, not an assertion). A rebuild (start-up) evaluates a getter once, then only those whose inputs a write of the previous pass changed (a getter whose inputs did not move is not evaluated again; before, a chain that never settled ran every getter of every entity up to 16 times: `Command.timeout_default` 1890 evaluations for 189 Commands, now 378). Tests: `eval_stats_1143.rs`, `eval_stats_host_1143.rs`, `seat_process.rs` (`stats_eval_...`, `the_boot_fact_eval_stats_false_...`).

**The event stream** (#1143; `native/src/http.rs`, `drivers.rs`, `membrane/packs/door.c1f`, `chat.c1f`, `chat_turn.c1f`; tests `host_loop.rs`, `chat_process.rs`).
Three pieces, all writes (no host callback):
- *A Request can answer open-ended.* `Request.stream = {id, status?, headers?}` writes the head of a `text/event-stream` response (default `Content-Type`,
  `Cache-Control: no-store`, no length, `Connection: close`) and keeps the connection; `Request.send = {id, event?, data}` appends one event
  (`event: <event>` when named, `data: <data as one line of JSON>`, a blank line); `Request.end = {id}` closes. A route asks for it with a reply
  `{status: 200, stream: True}` (the door's `answer-stream` setter writes `stream`; a reply without `stream` is still `respond`). The frames are queued on the
  engine's thread in write order, and the effect threads write them, so two sends never swap. Receipts: `stream_result`/`send_result`/`end_result`
  (`rc` 0, or 1 when the client went away, or 2 when there is no open stream); a failed write forgets the stream. No keep-alive comment and no write timeout
  (thresholds, not chosen).
- *A Command can deliver while it runs.* `Command.run = {id, args, partial: True}` pushes each read's complete lines of stdout (the unterminated tail at
  the end) as an outside birth `Chunk:<command eid>:<n>` ({cmd, id, n, data}), in the style of `Fetch`'s chunks: a VIRTUAL class, so never stored or journalled (what was derived from them while the turn ran is not needed again: the receipt is the answer); the receipt still carries the whole `stdout`. A run without `partial` makes none. An arriving entity now marks the readers of
  its class (`instances('Chunk')` recalculates), which a door request did not need until now.
- *The chat turn uses both.* The turn runs with `partial: True`; `ChatMessage.partial_text` (the `text_delta`s of the `stream_event` lines) and `partial_tools` (the
  `tool_use` blocks started) read ONE accumulator chunk, `Chunk:<command eid>:acc` (`text`, `tools`): each chunk parses its own lines (`Chunk.part`) and its setter `partial-in` appends them there, so a birth costs the same whatever came before (the old `ChatMessage.chunks` getter listed every live chunk at each birth: a turn of N chunks cost N squared; test `the_work_per_chunk_does_not_grow_with_the_chunks_already_born`); `ChatMessage.stream_view` is the view with those while the turn runs. The chunks and the accumulator are collected once the turn's command has ended (the command's in-flight effect holds them while it runs; after its receipt they are held by nothing: "Garbage collection of virtual entities").
`GET /membrane/chat/message/<id>/events`: 404 `{error}` for an unknown message; otherwise 200, then one event `message` per change of `stream_view`, whose data
is `{id, text, state (queued | running | done | error), response (the partial answer while running, null until a word is out; the final one when done), tools
(names; the final list when done), turn: {state, started, ended}}`. Events are snapshots (a missed one costs nothing), the last is the one with `state` done or
error, then the connection closes. The stream's `Request` is held by its open connection while the stream is open: it is collected only
after `end_result` (or a failed `stream`); a client that leaves early makes the next send fail, and the turn's own `end` still lands. The page (`chat_view.c1f`) reads the stream of a running message and polls it again only if the stream cannot be had.

**The session API** (#1143, swap step 2; `membrane/packs/door_session.c1f`, a family pack of the `session` family, loaded after `chat_turn`; tests `native/tests/session_1143.rs`, fixtures `tests/golden/session`).
The opencode session API the page speaks, over the chat's own machinery. **A session is a chat**: `membrane::Chat:session:<sid>` (kind `ChatSession`: `stitle`, `born`, `upd`), and a message the page sends is a `ChatMessage` whose KEY holds the session id, `membrane::Chat:session:<sid>:message:<id>` (docs/chat-keys.md: `GET /session/<sid>/message` is a key range of the index, no body read); one message is TWO rows of the API: the user row (the text) and the assistant row (the turn's tools and answer). Routes (the door matches on `Request.route`, so they answer on `/ui/serve/...` too):
`GET|POST /session`, `GET|PATCH|DELETE /session/<sid>`, `GET /session/status` (`{<sid>: {type: idle|busy}}`, a store answer: a session is busy while one of its turns is `running`), `GET /session/<sid>/message[?limit=N&before=<message id>]`, `GET /session/<sid>/message/<mid>`, `POST /session/<sid>/prompt_async` (204) and `/message` (200 `{info, parts}` when the turn ends), `POST /session/<sid>/abort` (true), `GET /event`, `GET /global/event`. Not built (404): `/session/<sid>/voice`, `/predict`, `/diff`, `/todo`, `/children`, `/init` and the other stubs. (`/agent` and `/config` are the opencode probes the door answers itself, `door.c1f`.) *The model* (`packs/door_session.c1f`, `chat_turn.c1f`, `door_models.c1f`): `GET /v1/models` lists the claude-agent rungs the launcher named (`cloud_models`) as `owned_by: membrane->claude-agent`, with or without a router (the page's picker reads that owner). A session holds a pick (`ChatSession.smodel`): `PATCH /session/<sid> {model: {modelID}}` or a `model` in the body of a message sets it (the message's pick sticks); the session row and the rows' `modelID` show it, else the SEAT'S MODEL: the seat-wide pick (`Minds:seat.loops`, what the page's first-run "Which model?" form and the gear window post as `{loops: <model>}` to `POST /membrane/options` or `/membrane/models`, OWNER only: a person gets the 403 `for the owner` and nothing changes; an unknown or ill-formed name is a 400 with the reason and the old pick stays; it is kept in the store, so it survives a restart and wins over the launcher's `minds` fact), else the launcher's default (`minds.seat_default`, or the launch fact `seat_default`; NONE by default: a message sent with no model chosen starts no process and the answer says no model is chosen, how to open the picker and, when the local Ollama lists no chat model, `ollama pull <name>`; `claude` in the developer mode: the name that runs with no flag). The turn runs the CLI on a claude name (developer mode); a model the local Ollama lists runs the OpenAI-compatible turn. For a claude name it runs the CLI on it: a name in the `claude-agent:` namespace (the 0.7 rungs' names) runs with `--model <the bare alias>`; the launcher's default (`claude`) runs with no flag (the CLI's own default); another rung runs under its own name; a model that is a `cloud_models` entry with another backend, or a tag the local backend lists, runs the OpenAI-compatible turn (see "The OpenAI-compatible turn"); any other name (an unknown one) is refused IN THE TURN (an error row that names it, nothing starts). The provider is always `membrane`. A streamed partial transcript (`voice` with `stream` and `final: false`) is answered 204 and starts no turn (nothing is stored); the final transcript is the turn. Not built: the agent pick (`build`/`plan` is ignored), `claudeContinue` (the CLI is not resumed: a turn is one run with no history, so "Continue" is a fresh message), a queue (two messages of one session run side by side), the think dial.
There are no users (docs/auth.md): no per-person chat; `POST /session` always makes a new session.
*Ids* are `<prefix>_` and 24 digits (the shape the page expects), derived from the message so no table is kept: a session `ses_<ms:13><request n:8>000`, a message's rows `msg_<ms><n>001` (user) and `...002` (assistant), parts `prt_...010` (the user's text), `...100` (the answer's text part), `...2jj` (tool j of the turn); events `evt_...`. Limits that follow: a request number above 99,999,999 and more than 100 tools in one turn. *Parts of the assistant row*: finished, the tools the model ran in call order (`tool` parts, `completed`, with input and output; the part's `time` is the turn's), then ONE text part, the CLI's final answer (the lead-in words the model wrote between tool calls are streamed but not stored: the row is rebuilt from the entities, `ChatMessage.oc_parts`); running, what the stream has shown so far. A failed turn is the error text as its text part and `info.error {name: Error, data: {message}}`; an aborted one `MessageAbortedError`. `info` carries `tokens` and `cost` of the CLI's result line.
*The event streams*: `Request.send` takes `{id, frames: [{event?, data}, ...]}` (several frames in one write, queued in order). The engine allows ONE write of a (entity, property) in a cascade (a second is refused: "loop: ... already written this round"), except a driver verb (`send`, `run`, ...): a command, one effect per write, run in write order. So each producer writes its OWN bus entity (`SesBus:start-<id>`, `SesBus:chunk-<id>-<n>`, `SesBus:end-<id>`: virtual entities, a list of `{type, id, properties}`), a chunk of the CLI's output and the turn's end can land in one round without one dropping the other, and the bus's setter writes the frames to every open stream (`Request.ev_on`), wrapped for `/global/event`. A chunk taken after its turn is over says nothing (the end's final parts carry the words). Three producers: the message's start (`queued`: user message and part, `session.updated`, busy, the assistant's message, `session.updated`), each chunk of the CLI's output (`Chunk.oc_go`: the answer's words, the text part opened EMPTY with the first, then a `message.part.delta` per read; a tool's part `running` when it starts and `completed` when its result line comes, up to 8 per read), and the turn's end (`ChatMessage.oc_fin`: the final parts with the SAME ids, so the page's rows are replaced, the message completed, `session.status` idle, `session.idle`, `session.updated`). A stream that opens later sees only what follows (`server.connected` first); the page loads the rows after it connects. Not sent: `session.diff`, no step parts, no keep-alive ping, no `membrane.*` events; the lead-in text of a turn is one text part while it streams and the final answer replaces it; inside one read of the CLI's output the words come before the tools; a turn REFUSED before it started (no `chat_claude_bin`) ends in the start's own cascade, so its end is not on the stream (the rows and `/session/status` have it).
*The shape comparer* (`session_1143.rs`, `shape_misses`): the answers are compared with recorded answers of the 0.7 seat (the shape the page expects) (`tests/golden/session/*.json`; no model): every key of the fixture in the answer with the same JSON type, extra keys allowed, a `null` in the fixture accepts any type, each element of an answer's list matches SOME element of the fixture's list; values (ids, times) are never compared. `tests/js/page_boot.test.mjs` shows the page itself (headless Chrome) creating a session and following `/ui/serve/event`.

## Threading
One engine behind one lock; the loop runs on the main thread; the door's accept and connection threads are in `http.rs`; an effect runs on its own driver thread (`effect_workers` slots for the slow ones).
The command name lives in the `[[bin]] name` of `native/Cargo.toml` (`CARGO_BIN_EXE_cliffvm` in the tests and the `cliffvm-<version>` build id follow it).

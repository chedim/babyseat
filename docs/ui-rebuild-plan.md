# The page as c1f view packs: status per slice (#1143)

Status: the page of the release is built and shipped as c1f. The first draft of this file was a plan with round estimates, constants and twelve open decisions; the decisions were answered by building, and the plan is not repeated here
(it is in git history). What is true now is below, slice by slice. Related: docs/cliffhanger-fields.md section 9 (the browser VM's host API), docs/settings-groups.md (the Settings view), docs/graph-link.md (what the page tells the seat);
the disabled 3D view is the pack `membrane/apps/field.c1f/field_view.c1f` (its header) and the feed routes in `membrane/packs/door_fieldvm.c1f`.

**What the page is.** `membrane/apps/barest.c1f/ui/` holds `index.html` (a bootstrap: one mount node), `boot.js` (starts the engine, feeds it the seat's packs and facts, runs ONE 100 ms clock), `app.css`, and the browser VM
(`fieldvm.js`, `fieldvm_core.js`, `fieldvm_core_bg.wasm`, `fieldvm_version.js`, about 1.2 MB of wasm: the seat's own Rust VM compiled). Everything the person sees is a view pack drawn with `DomNode` entities. The screens are Chat and Settings.
The old JavaScript page and its folder `membrane/ui/` are gone.

**The shell and the view-pack contract: the whole barest page is c1f.** `ui/index.html` is a bootstrap (one mount node) and `ui/boot.js` starts the engine, loads the seat's packs (a pack that imports another loads after it), feeds `Shell:main` {view, sid, load_errors, then open} and runs ONE 100 ms clock. `shell_view.c1f` owns the layout, the nav, the status line (a poll of `GET /session/status`: connected, a turn running), the errors (text, role alert), the theme (system, light, dark on the `<html>` element) and the slide-over panel. `chat_view.c1f`, `settings_view.c1f` and `link_view.c1f` are the page's packs in the release; `field_view.c1f` (`membrane/apps/field.c1f`) is the third view and is disabled. There is no old JavaScript page and no switch between renderers: the old page (`membrane/ui/`) is deleted and lives in git history.
A view pack, to plug into the page, `IMPORT shell_view 1` (a class a pack writes to must be DECLARED by some loaded pack, a getter is enough: a write to an undeclared class is dropped silently by the engine, which cost an hour here) and: (1) registers `Nav:<name>` {title, order} in a setter on `Shell.open`; (2) draws its root DomNode with `parent = 'DomNode:shell:slot:<name>'` when `Nav:<name>.active` first becomes true (lazy: the Field view is not drawn until it is shown) and writes `('Nav:<name>').filled = True` (the shell's placeholder text goes away); (3) does no periodic work while `prop('Nav:<name>', 'active') == False`. The Settings slot is the shell's own placeholder (text `Settings`) until a pack registers over it. No view knows a person or a permission: everyone who can reach the page is the admin; a write the seat refuses is shown as the seat's own text.
The shared SLIDE-OVER DETAIL PANEL: a view writes `Panel:detail` {owner, title, sub, note, rows: [{key, label, text, target?, head?}], open: true}; it slides in from the right over the views, a scrim covers the rest (a click on it, Close or Esc writes `open = false`), a long `text` is cut at `max_chars` and expands (`Show all`), a row with `target` is a link (the shell writes `picked`), and the view reacts in its own setters on `Panel.open` / `Panel.picked` for its `owner`. The field view opens it on a node click (id, class, properties from `GET /ui/fieldvm/entity?eid=`, edges from `/ui/fieldvm/edges`). The chat is covered, not unmounted (a draft survives). There is ONE chat (operator 2026-11-14): no session list, no New session; the chat view reads `GET /membrane/chat/messages` with no `sid` (every turn, newest page first; the seat's imported history is its older pages) and sends `POST /membrane/chat/message {text}`. The routes keep their optional `sid` for other clients; the page does not use it. The host cancelled every wheel over every element it made (so the log did not scroll): a wheel is now the pack's only on an `svg` element (the field's zoom), and everything else scrolls natively (`tests/js/chat_scroll.test.mjs`). A call cannot wedge a view: every chat call carries `timeout_s` (fact `chat_poll_timeout_s`), so a poll that never answers is aborted, said in text and asked again (the cause of a finished turn staying "Waiting for a turn…").
Constants tried, not decided: `shell_status_ms` 3000, `shell_panel_chars` 200, `chat_poll_timeout_s` 10, the 100 ms clock, the 520 px panel width.

## Markdown, Stop and tool rows in the c1f chat

- **Markdown** (`membrane/apps/barest.c1f/markdown.c1f`, tests `tests/js/markdown.test.mjs`, `tests/js/markdown_page.test.mjs`): the answer AND the person's message are markdown, drawn as DomNodes with text nodes only (never HTML). Classes: `Md` (the message, cuts at `cap` = 12000 characters; the rest is a plain preview with "Show all"), `MdChunk` (a fenced code block, or up to 40 lines of prose; a chain: each chunk hands the rest of the text to the next, at most 120), `MdBlock` (paragraph, heading, hr, quote, list, table, table row; lists and quotes recurse to depth 4), `MdLine` (inline code, bold, italic, strikethrough, `[text](url)` and bare http(s) links, at most 48 tokens per line), `MdPaint` (the one writer of nodes). Every entity evaluates once per change of its own text, so streaming re-draws only what changed and an unchanged text is zero writes; a message can never exceed the 100,000-step budget because every stage is bounded by a cut (40 lines, 64 pieces, 48 tokens, 12 columns).
- c1f has no `split`, no index in a comprehension, no `%` and no nested `for`; the pack stands in with `lines(replace(t, sep, '\n'))`, list literals `0..63` and NUL-delimited token streams (see the pack's header).
- **Stop**: `POST /membrane/chat/message/<id>/abort` (packs/chat.c1f; the setter that kills the CLI is in chat_turn.c1f, which imports `proc`) ends the running turn as an error whose answer is what was said so far plus "(stopped from the page)"; the page's composer shows Stop only while a turn runs.
- **Tool rows**: `details.tools-run` in the chat: "N tools", each with its name and its WHOLE input (wrapped); the fact `chat_tool_chars`, when set above 0, cuts it to that many characters (the legacy chat cut at 90; no cut is the default). While a turn RUNS its tools are an always-visible list under the pending line (a `details` cannot be opened by a pack), each with its result once it has one, and a brain turn's live text (`live`) is a muted block; the finished turn folds them.
- Host additions (fieldvm.js, listed as decisions): tags `blockquote hr h5 h6`, attributes `target rel`, and a pack's `copy` write on a node (`{text, at}`) puts the text on the clipboard.
